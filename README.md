# Intranet GT

Intranet corporativa: monolito Next.js (App Router, TypeScript) + MySQL con toda la logica de datos en procedimientos almacenados. Patron "MAESTRO DE MAESTROS" para catalogos.

Diseño completo (modelo de datos, RBAC, SSO, roadmap por fases) en `.claude/plans/harmonic-splashing-bentley.md`. Implementado hasta ahora:

- **Fase 1**: esquema base, autenticacion con la regla de sesion por horario laboral, layout de la intranet (sidebar/topbar/dashboard).
- **Fase 2**: RBAC real (aplicaciones + matriz de permisos por rol), notificaciones (incluye difusion a un usuario, un rol, un area o todos), y pantallas de `/administracion` (usuarios, roles/areas, aplicaciones, maestros, permisos, envio de notificaciones).
- **Fase 3**: primer modulo de negocio real, Directorio Corporativo (`/rrhh/directorio`, administrado por RRHH) — plantilla de como se ve un modulo con tablas propias y permisos que varian por rol (RRHH admite/edita, el resto de la empresa solo consulta).
- **Modulo RRHH - Contratos**: contratacion, contratos de planilla (fulltime/parttime) y locadores, vencimientos, y firma digital via link publico sin login (`/rrhh/contratos` para RRHH, `/contratos/firmar/[token]` para la persona contratada).
- **Maestro de contratos** (`/rrhh/contratos/plantillas`): el gerente de RRHH (nivel `ADMIN` sobre `RRHH_CONTRATOS`) carga el contenido legal de cada regimen de contrato (titulo, parrafo de identificacion de las partes y clausulas) una sola vez; ese contenido es la base con la que se genera cada contrato individual, con encabezado/pie de pagina de marca y numero de contrato autogenerado en todo el PDF — ver seccion "Contratos (RRHH)".
- **Modulo de Cuentas** (`/facturacion/cuentas`, area FACTURACION): catalogo de cuentas de la empresa (bancarias en soles/dolares por banco, cuenta de detracciones, y saldos a favor de IGV/Renta) con libro de movimientos (ingresos/egresos) y saldo calculado por el servidor — ver seccion "Cuentas (Facturacion)".
- **Modulo de Pasivos** (`/facturacion/pasivos`, area FACTURACION): deudas, prestamos, lineas de credito y letras protestadas con su plan de pagos (cuotas), y una vista de plan de pagos priorizada con alertas de salud de caja — ver seccion "Pasivos y Compras (Facturacion)".
- **Modulo de Compras** (`/facturacion/compras`, area FACTURACION): proveedores, compras con pagos parciales, y pagos a contratos de RRHH (haberes/honorarios) organizados por contrato — ver seccion "Pasivos y Compras (Facturacion)".
- **Modulo de Proyectos y Servicios** (`/facturacion/proyectos`, area FACTURACION): costeo y margen por proyecto/servicio, juntando mano de obra (horas de locador + asignacion manual), compras vinculadas e ingresos, con dashboard de costo/margen a hoy vs al cierre (presupuesto) — ver seccion "Proyectos y Servicios (Facturacion)".
- **Modulo de Pagos Recurrentes** (`/facturacion/pagos-recurrentes`, area FACTURACION): cronograma de gastos que se repiten periodo tras periodo (alquiler, internet, software, seguros...), monto fijo o variable, con cualquier frecuencia (mensual, trimestral, anual...), alertas de vencimiento y opcionalmente linkeados a un proyecto — ver seccion "Pagos Recurrentes (Facturacion)".

## Despliegue en Railway

La app corre en un servicio de Railway (contenedor efimero: el filesystem se reinicia en cada deploy/restart). Dos cosas necesitan configuracion aparte del deploy normal:

**1. Volume para `UPLOADS_DIR`** (para que los PDFs/firmas de contratos no se pierdan):
- En el servicio de la app, pestaña **Volumes** → crea uno, ej. montado en `/data`.
- En las variables de entorno del servicio, setea `UPLOADS_DIR=/data/uploads`.
- Redeploy. A partir de ahi, todo lo que se guarde en esa carpeta persiste entre deploys.

**2. Cron Job para `/api/cron/contratos-por-vencer`**:
- En el mismo proyecto de Railway, **New → Empty Service** (no necesita build propio).
- En **Settings** de ese servicio, en **Cron Schedule**, pon algo como `0 8 * * *` (8am todos los dias).
- Como **Start Command** (o Deploy → Custom Start Command):
  ```
  curl -s -H "x-cron-secret: $CRON_SECRET" https://TU-SERVICIO.up.railway.app/api/cron/contratos-por-vencer
  ```
- Copia `CRON_SECRET` (la misma variable que usa el servicio principal) a las variables de entorno de este servicio de cron, para que `$CRON_SECRET` se resuelva.
- Railway solo ejecuta el start command cuando toca el schedule (no queda corriendo entre medio), asi que no consume recursos fuera de esos segundos al dia.

## Regla de sesion

- Dentro del horario laboral efectivo del usuario (`HORARIO_LABORAL`, por rol con override opcional por usuario): la sesion se renueva sola en cada actividad y expira a la hora de fin de turno de hoy, sin importar inactividad.
- Fuera de ese horario (o si no hay horario configurado): la sesion se cierra tras 30 minutos de inactividad.
- El checkbox "Recordar mi usuario" del login solo precarga el campo usuario (via `localStorage`); la clave nunca se guarda fuera del gestor de contraseñas del navegador.

## RBAC

- `AREA` -> `ROL` (area + sub-rol) -> `ROL_APLICACION_PERMISO` (rol x aplicacion x nivel). Agregar area/aplicacion nueva es solo `INSERT`s.
- **Crear con codigo unico** (`SP_AREA_CREAR`, `SP_ROL_CREAR`, `SP_APLICACION_CREAR`, `SP_MAESTRO_CREAR`, y `SP_USUARIO_CREAR` solo para `CORREO` — el login se autogenera con sufijo y nunca choca): si ya existe una fila con ese codigo (o `ID_AREA`+codigo para `ROL`), la SP hace no-op silencioso (el `OUT` id queda `NULL`, mismo criterio que el resto del sistema — no se usa `SIGNAL`) y el repositorio (`src/lib/db/repositories/*.repository.ts`) revisa ese `NULL` y lanza un `Error` con mensaje claro en vez de dejar pasar el error crudo de MySQL (`Duplicate entry ... for key ...`). `crearUsuarioAction` lo captura y lo muestra inline (`CrearUsuarioForm`, via `useActionState`); el resto de acciones de creacion en `/administracion` no tienen ese formulario con estado — el error se ve en la pantalla de error de Next, pero con el mensaje en español en vez del crudo de SQL.
- Al crear una `APLICACION` (`SP_APLICACION_CREAR`), el rol `SUPER_ADMIN` recibe automaticamente nivel `ADMIN` sobre ella — no hay bypass hardcodeado en el codigo.
- El dashboard y el sidebar solo muestran las aplicaciones donde el usuario tiene algun nivel distinto de `SIN_ACCESO` (`SP_APLICACION_LISTAR_VISIBLES`, agrega el maximo privilegio entre todos sus roles).
- `/administracion/*` requiere nivel `ADMIN` sobre la aplicacion `ADMINISTRACION` (`requirePermiso`, ver `src/lib/auth/require-permiso.ts`). `/rrhh/contratos` requiere `LECTURA`+ sobre `RRHH_CONTRATOS` (solo RRHH; a diferencia del directorio, no es publico para otras areas porque incluye datos bancarios/remuneracion). Crear/editar contratos pide `ESCRITURA`+; `/rrhh/contratos/plantillas` (maestro de contratos) pide `ADMIN` — solo el gerente de RRHH define el contenido legal, cualquiera con `ESCRITURA` solo elige entre los regimenes ya cargados.
- Por encima del RBAC por aplicacion existe el rol **SUPER_ADMIN** en si mismo, verificable con `esSuperAdmin(idUsuario)`/`requireSuperAdmin()` (`src/lib/auth/require-permiso.ts`) para acciones que ni siquiera un `ADMIN` de un modulo puntual deberia poder hacer — hoy solo el logo de la empresa (`/administracion/empresa`).
- `APLICACION.VISIBLE_TODOS_LOS_ROLES = 1` (usado por `RRHH_DIRECTORIO`) le da a **cualquier** usuario un piso de `LECTURA` sobre esa app, sin necesitar una fila en `ROL_APLICACION_PERMISO` — el nivel real de un rol (ej. RRHH con `ESCRITURA`/`ADMIN`) siempre prevalece si es mayor. Reutilizable para futuras apps "de toda la empresa".
- El directorio ademas tiene reglas de visibilidad de campo por persona (`src/lib/rrhh/visibilidad-directorio.ts`): cualquiera ve datos basicos de contacto de cualquier persona; el detalle completo (documento de identidad, pais/ciudad, direccion, telefono, usuario) solo lo ve RRHH, la propia persona, o su jefatura si es de la misma area. Edicion: RRHH edita todo de cualquiera; cada quien edita solo sus propios datos de contacto (telefono/direccion/foto) — puesto/documento/pais/ciudad/fecha de ingreso los controla RRHH.
- Identidad de la persona (`RRHH_EMPLEADO`): tipo de documento (catalogo `TIPO_DOCUMENTO_IDENTIDAD` — DNI, Carné de Extranjería, Pasaporte, RUC) + numero (`NRO_DOCUMENTO`), y pais/ciudad como catalogos jerarquicos (`MAESTRO_MAESTRO` con `TIPO_MAESTRO='CIUDAD'` colgando de su `PAIS` via `ID_PADRE`). El selector de pais es un combo con busqueda sobre las ~250 filas (`src/components/ui/ComboBusqueda.tsx`); el de ciudad es en cascada, recarga via `GET /api/maestros/ciudades?idPais=` (`SP_MAESTRO_LISTAR_HIJOS`) cada vez que cambia el pais elegido (`src/components/rrhh/SelectorPaisCiudad.tsx`). Para agregar mas ciudades (el seed solo cubre Peru completo + los paises mas frecuentes en contratacion), usa `/administracion/maestros?tipo=CIUDAD`, que pide el pais padre en el propio formulario de alta.

## Contratos (RRHH)

- **Regimenes** (`TIPO_CONTRATO`): `PLANILLA_FULLTIME`, `PLANILLA_PARTTIME`, `LOCADOR` — este ultimo con 4 variantes de pago (`TIPO_PAGO_LOCADOR`): `POR_HORA` (tareo por proyecto), `POR_PROYECTO` (monto fijo total ligado a un proyecto/entregable), `MENSUAL` y `POR_JORNADA` (montos recurrentes).
- **Maestro de contratos** (`/rrhh/contratos/plantillas`, requiere `ADMIN`): antes de poder crear un contrato de un regimen, tiene que existir una plantilla **activa** para ese regimen exacto (`RRHH_CONTRATO_PLANTILLA` + `RRHH_CONTRATO_PLANTILLA_CLAUSULA`, resuelta por `SP_RRHH_PLANTILLA_OBTENER_ACTIVA`) — `crearContratoAction` lo bloquea si falta, y `/rrhh/contratos/nuevo` ya avisa en la UI que regimenes les falta plantilla. Cada plantilla tiene titulo del documento, un parrafo de identificacion de las partes y N clausulas ordenadas (titulo opcional + contenido). El texto usa placeholders `{{TOKEN}}` (ver `src/lib/rrhh/plantilla-tokens.ts` para la lista completa — datos del empleador, de la persona, fechas cortas y largas, y bloques dinamicos como `{{DETALLE_REMUNERACION}}`/`{{DETALLE_PAGO}}`/`{{DETALLE_PAGO_FILAS}}` que se arman solos segun los conceptos/proyectos/tarifa del contrato). El bloque de firma (nombre, documento, imagen de la firma, representante legal) es fijo en codigo, no editable via plantilla — separa el contenido legal editable de la parte de verificacion.
  - **Tablas dentro de una clausula**: una linea de la forma `| celda | celda |` (2 columnas = clave/valor, 3+ = encabezado + filas) dentro del `CONTENIDO` de una clausula se detecta y se dibuja como tabla con bordes en vez de texto corrido (`PdfWriter.tabla()`, invocado desde `parrafo()`) — asi es como se ven, por ejemplo, "DATOS DE INGRESO" o la tabla de "PAGOS" de los acuerdos de locador.
  - **Logo/branding**: es configuracion **general de la empresa**, no por plantilla — un solo logo para todos los contratos, sin importar el regimen (`CONFIGURACION_EMPRESA`, fila singleton). Se administra desde `/administracion/empresa`, y solo un usuario con rol **SUPER_ADMIN** puede subirlo o cambiarlo (`requireSuperAdmin()` en `src/lib/auth/require-permiso.ts`, respaldado por `SP_USUARIO_ROL_LISTAR_ACTIVOS_POR_USUARIO`) — ni el gerente de RRHH con `ADMIN` sobre `RRHH_CONTRATOS` puede tocarlo. `resolverPlantillaContrato`/`cargarPlantillaPorId` (`src/lib/rrhh/resolver-plantilla.ts`) lo adjuntan a cualquier plantilla al generar el PDF.
  - **Vista previa de ejemplo**: boton "Ver ejemplo (PDF)" en el listado y en el detalle de cada plantilla (`GET /api/contratos/plantillas/[id]/vista-previa`, requiere `ADMIN`) genera el PDF completo con datos de un colaborador/proveedor ficticio (Juan Carlos Pérez Ejemplo), para que RRHH vea como quedaria antes de activarla — no toca ningun contrato ni empleado real.
- RRHH crea el contrato (`/rrhh/contratos/nuevo`) en estado `BORRADOR`, con cargo/fechas (inicio y fin son obligatorias) y, si es `LOCADOR` mensual/por jornada/por proyecto, tarifa+proyecto de una vez. El formulario es dinamico (`NuevoContratoForm.tsx`): los campos cambian segun el `TIPO_CONTRATO`/`TIPO_PAGO_LOCADOR` elegido, y lista a **todo** el directorio (no solo a quienes ya tienen datos completos).
  - **Identidad minima** (`src/lib/rrhh/identidad.ts`, `tieneIdentidadCompleta`/`tieneIdentidadCompletaContrato`): lo unico obligatorio para generar un contrato es el documento de identidad (tipo + numero) — direccion/pais/ciudad **no** son obligatorios, no son parte del cuerpo de ningun modelo de contrato (`{{DIRECCION}}`/`{{PAIS}}`/`{{CIUDAD}}` se resuelven a "-" si faltan, ver `plantilla-tokens.ts`). Si a la persona elegida le falta el documento, el propio formulario muestra los campos para completarlo ahi mismo (mismo `SelectorPaisCiudad` que usa la ficha de empleado para direccion/pais/ciudad, ahi opcionales) — `crearContratoAction` fusiona lo que llega con lo que ya tenia, guarda la ficha (`upsertEmpleado`) y recien entonces crea el contrato; si el documento sigue incompleto, no-op silencioso.
  - **Acceso directo desde el perfil**: `/rrhh/directorio/[idUsuario]` tiene una seccion "Contratos" (visible con `RRHH_CONTRATOS` `ESCRITURA`) con boton "Crear contrato" hacia `/rrhh/contratos/nuevo?usuario={id}` (persona preseleccionada) y, para cada contrato `FIRMADO`/`VENCIDO` de esa persona, un link "Renovar" hacia su detalle (la seccion de renovar ya vive ahi, no se duplica el formulario).
  - **Puesto y fecha de ingreso ya no son texto libre** (`028_empleado_calculado.sql`, quita `RRHH_EMPLEADO.PUESTO`/`FECHA_INGRESO` como columnas propias): "Puesto" en la ficha del colaborador es el nombre de su rol principal (`ROL.NOMBRE` via `USUARIO_ROL.ES_PRINCIPAL=1`, la misma columna que ya se calculaba como `ROL_NOMBRE` para RBAC — cambiar el puesto de alguien es asignarle otro rol desde `/administracion`), y "Fecha de ingreso" es la fecha de inicio de su contrato mas antiguo (`MIN(RRHH_CONTRATO.FECHA_INICIO)`, cualquier tipo). Ninguno de los dos se puede escribir a mano ya en ningun lado (ni RRHH ni la propia persona) — `SP_RRHH_EMPLEADO_OBTENER` calcula ambos y los sigue exponiendo bajo los mismos nombres de columna (`PUESTO`/`FECHA_INGRESO`) para no tocar la UI de solo-lectura, mismo truco de alias que `NOMBRE_PROYECTO`/`ACREEDOR`.
  - **Jornada** (solo `PLANILLA_FULLTIME`/`PLANILLA_PARTTIME` — un locador no tiene horario por ley, no hay subordinacion): dias laborales + hora de inicio/fin + una nota libre opcional, capturados por contrato (`RRHH_CONTRATO.DIAS_LABORALES`/`HORA_INICIO`/`HORA_FIN`/`NOTA_JORNADA`), disponibles como placeholders (`{{DIAS_LABORALES}}`, `{{HORA_INICIO}}`, `{{HORA_FIN}}`, `{{NOTA_JORNADA}}`) para que la clausula de jornada de la plantilla los use.
  - **Funciones, solo PLANILLA, editable hasta antes de firmar** (mismo criterio que Jornada -- un locador de servicios no tiene "funciones" de puesto, no hay subordinacion, ver clausula 7 de cada Acuerdo de Servicios): `SP_RRHH_CONTRATO_ACTUALIZAR_FUNCIONES` deja agregar/corregir `RRHH_CONTRATO.FUNCIONES` mientras el contrato sigue `BORRADOR`/`PENDIENTE_FIRMA` -- no-op silencioso si ya esta `FIRMADO` o si es `LOCADOR` (`ID_TIPO_PAGO_LOCADOR IS NOT NULL`). `SP_RRHH_CONTRATO_CREAR` fuerza `FUNCIONES=NULL` para `LOCADOR` sin importar lo que llegue del formulario, mismo criterio que `ES_INTERNO` forzando `ID_CLIENTE=NULL` en Proyectos. En el detalle del contrato (`/rrhh/contratos/[id]`) la seccion "Funciones" ni siquiera se muestra para `LOCADOR`; para `PLANILLA` se ve como formulario editable antes de firmar, y como texto de solo lectura despues. La plantilla de `LOCADOR` (`017_plantillas_locador_tablas.sql`) ya no trae la fila "FUNCIONES ESPECÍFICAS" en "1. DATOS DE INGRESO".
- **PDF del contrato**: encabezado con logo + RUC/telefono/correo de la empresa + numero de contrato (`CONT#AAAA-NNNN`, autogenerado desde `ID_CONTRATO` y el año de creacion — `formatearNroContrato()`), repetido en todas las paginas; pie de pagina con razon social + fecha/hora de generacion del PDF + "Pagina X de Y" en todas las paginas. El monto de la remuneracion tambien esta disponible en letras (`{{TOTAL_REMUNERACION_LETRAS}}`, ej. "Seiscientos y 00/100 Soles" — `src/lib/rrhh/numero-a-letras.ts`, conversion propia sin dependencia externa). El texto de los parrafos se justifica (ambos margenes parejos), salvo la ultima linea de cada parrafo.
  - **Firma**: `PLANILLA_FULLTIME`/`PLANILLA_PARTTIME` usan un recuadro con borde por cada parte, uno debajo del otro (`PdfWriter.firmaEnRecuadro()`); `LOCADOR` (los 4 tipos de pago) usa firma lado a lado sin recuadro, cada una sobre su propia linea (`PdfWriter.firmasEnColumnas()`) — replica el estilo real de cada familia de documento.
- **Ingresos, segun tipo** (se agregan despues de crear, desde el detalle del contrato):
  - `PLANILLA_FULLTIME`/`PLANILLA_PARTTIME`: N lineas de **concepto remunerativo** (`RRHH_CONTRATO_CONCEPTO`, catalogo `CONCEPTO_REMUNERATIVO` editable desde `/administracion/maestros`) — ingreso base, bono, movilidad, bonificacion familiar, etc. El total es la suma.
  - `LOCADOR` + `MENSUAL`/`POR_JORNADA`/`POR_PROYECTO`: un solo monto (`TARIFA` + `RRHH_CONTRATO.ID_PROYECTO`, enlazado a un `PROYECTO`/servicio existente en vez de texto libre — obligatorio solo para `POR_PROYECTO`, opcional para `MENSUAL`/`POR_JORNADA` ver "Nombre de proyecto = Proyecto/Servicio real" en la seccion "Proyectos y Servicios" mas abajo).
  - `LOCADOR` + `POR_HORA`: puede tener **varios proyectos**, cada uno con su propia tarifa/hora (`RRHH_CONTRATO_PROYECTO.ID_PROYECTO`, tambien obligatorio y enlazado a un `PROYECTO` existente). Las horas trabajadas se cargan manualmente por proyecto/periodo (`RRHH_CONTRATO_HORAS`) y el monto se calcula solo (horas × tarifa del proyecto) — la carga automatica desde el Excel que exporta Clockify queda pendiente (falta que nos pases un archivo de ejemplo para mapear las columnas); por eso ya existe `RRHH_EMPLEADO.CORREO_CLOCKIFY` como identificador de la persona en Clockify, para cuando se conecte.
- Desde el detalle genera un **link publico de un solo uso** (`SP_RRHH_CONTRATO_GENERAR_LINK`, token UUID valido 7 dias) y se lo comparte a la persona.
- La persona entra a `/contratos/firmar/[token]` **sin necesitar cuenta ni login** (esta ruta esta excluida de `proxy.ts`); si a su ficha le falta documento/direccion/pais/ciudad, no puede firmar todavia (pantalla de aviso en vez del formulario). Puede leer el contrato completo antes de firmar via el boton "Leer el contrato completo (PDF)" (`GET /api/contratos/publico/[token]/vista-previa`, genera el mismo PDF sin firma) y debe marcar un checkbox de confirmacion de lectura (validado tambien server-side) antes de poder enviar. Completa sus datos bancarios — el banco se elige de un catalogo con busqueda (`TIPO_MAESTRO='BANCO'`, `RRHH_CONTRATO.BANCO` sigue siendo texto libre) — y firma dibujando en un canvas responsive o subiendo una foto/imagen de su firma (`FirmaInput.tsx`, normalizada a PNG en el navegador).
  - **Datos bancarios precargados si ya los tenia** (`FirmarContratoForm.tsx` recibe `nroCuentaInicial`/`cciInicial`/`bancoInicial` desde `RRHH_CONTRATO` en vez de arrancar siempre en blanco): si el contrato ya trae `NRO_CUENTA`/`CCI`/`BANCO` (porque `SP_RRHH_CONTRATO_CREAR`/`SP_RRHH_CONTRATO_RENOVAR` ya los copiaron del contrato anterior de esa persona, ver abajo), el formulario de firma arranca con esos valores en vez de vacio -- siguen siendo editables por si la persona cambio de cuenta o de banco.
- Al enviar, el servidor resuelve la plantilla activa del regimen (`resolverPlantillaContrato`) y genera el PDF final en un solo paso (`src/lib/rrhh/generar-contrato-pdf.ts`, con `pdf-lib`) reemplazando los placeholders de la plantilla con los datos del contrato + la firma ya embebida, lo guarda en `UPLOADS_DIR/contratos/`, marca el contrato `FIRMADO` e invalida el token. El PDF se descarga automaticamente en el navegador de la persona.
- "Renovar" (solo disponible sobre contratos `FIRMADO`/`VENCIDO`, tambien exige fecha de fin) crea un contrato nuevo enlazado via `ID_CONTRATO_ANTERIOR`, copiando cargo/funciones/tarifa/datos bancarios **y** los conceptos/proyectos actuales (no las horas, son de cada periodo), y marca el anterior como `RENOVADO`. Los montos se ajustan despues desde el detalle del contrato nuevo.
- **Un contrato nuevo (no renovacion) tambien jala los datos bancarios** si la persona ya tenia alguno anterior: `SP_RRHH_CONTRATO_CREAR` busca el contrato mas reciente de ese `ID_USUARIO` (cualquier tipo/estado) que ya tenga `NRO_CUENTA` capturado y lo copia al nuevo -- cubre el caso de alguien que pasa a un contrato de tipo distinto (ej. planilla a locador) sin que tecnicamente sea una "renovacion". Igual de editable en la pantalla de firma que el caso de renovacion.
- **Alertas de vencimiento y de firma pendiente** (`/rrhh/contratos`): 3 niveles de urgencia sobre los contratos por vencer (proximos dias / siguiente semana / dentro del mes, calculados client-side sobre el mismo fetch de 30 dias) mas una alerta aparte para contratos que aun no llegan a `FIRMADO` (`BORRADOR` o `PENDIENTE_FIRMA`) — no es lo mismo "por vencer" (contrato ya vigente) que "sin cerrar" (contrato que ni siquiera se firmo). Los mismos 3 niveles se repiten como un icono junto a la fecha "Fin" de cada fila de la tabla (rojo/ambar/azul, mismo `Map<ID_CONTRATO, dias>` armado sobre el mismo fetch de 30 dias, sin otra consulta) — `<title>` del SVG da el tooltip nativo al pasar el mouse con la fecha exacta y cuantos dias faltan, sin JS ni libreria de iconos.
- **Filtro por estado y descarga directa** (`/rrhh/contratos?estado=CODIGO`): chips de filtro sobre el listado (uno por cada `ESTADO_CONTRATO`, incluido "Todos") para ubicar rapido, por ejemplo, solo los `FIRMADO`; la tabla agrega una columna "Documento" con link directo de descarga (`/api/contratos/[id]/documento`) en cada fila cuyo estado sea `FIRMADO`, sin tener que entrar al detalle de cada contrato.

## Planilla Mensual (RRHH)

Antes de este modulo, el sistema se documentaba a si mismo como "no es un motor de planillas (no calcula AFP/ONP/impuestos)" -- este es exactamente ese hueco: una corrida mensual que junta **todos** los colaboradores sin importar el regimen (`PLANILLA_FULLTIME`/`PARTTIME` o cualquiera de los 4 `LOCADOR`), calcula automaticamente AFP/ONP/EsSalud/Renta con tasas legales, deja editar los montos antes de emitir (por persona o para toda la planilla), controla si ya se remitieron los aportes a SUNAT, y emite boleta de pago (5ta) o recibo por honorarios (4ta) en PDF con el logo/marca de la empresa (mismo mecanismo que los contratos). App nueva `RRHH_PLANILLA` (`db/seed/035_aplicacion_planilla.sql`, mismo criterio de acceso restringido que `RRHH_CONTRATOS`: solo RRHH, no `VISIBLE_TODOS_LOS_ROLES`).

- **No reemplaza el flujo de pago existente, lo orquesta**: `RRHH_CONTRATO_PERIODO_PAGO`/`RRHH_CONTRATO_HORAS` siguen siendo la fuente del bruto y del boton de pago individual en `/rrhh/contratos/[id]` -- `generarPlanillaMensualAction` (`src/lib/actions/rrhh-planilla.ts`) reusa `generarPeriodosPendientes` (`periodos-pago.ts`) para asegurar que exista el periodo del mes de cada contrato en vez de reimplementar esa logica, y solo agrega una capa encima: descuentos legales, control de aportes, y emision. `RRHH_PLANILLA_DETALLE.TIPO_REFERENCIA/ID_REFERENCIA` (mismo patron generico que `PASIVO`) enlaza cada fila a su `RRHH_CONTRATO_PERIODO_PAGO` de origen; para `LOCADOR POR_HORA` (que no usa periodo_pago) el enlace es 1-a-N via `RRHH_PLANILLA_DETALLE_HORAS`, sumando las horas del mes que compartan moneda -- si un contrato tiene horas en mas de una moneda el mismo mes, se excluye de la generacion automatica (queda para carga manual, no hay forma segura de sumar montos en monedas distintas en una sola fila).
- **Tasas legales versionadas, no hardcodeadas** (`RRHH_PLANILLA_PARAMETRO` + `_TRAMO_RENTA5TA` + `_AFP_FONDO`, `039_rrhh_planilla_parametro.sql`): UIT, ONP/EsSalud/AFP (aporte obligatorio + prima de seguro + comision por fondo)/Renta 4ta/tramos de Renta 5ta cambian cada año (UIT) o trimestre (tope asegurable AFP, publicado por la SBS) -- ledger de solo insertar, mismo patron que `TIPO_CAMBIO_HISTORICO` ("vigente" = la fila mas reciente cuya `FECHA_VIGENCIA_DESDE` ya paso, `SP_RRHH_PLANILLA_PARAMETRO_OBTENER_VIGENTE`). Corregir una tasa es crear una version nueva desde `/rrhh/planilla/parametros` (requiere `ADMIN` de `RRHH_PLANILLA` -- decision explicita de que sea Jefatura de RRHH quien las administra, no Super Admin), nunca se edita una version existente. El seed inicial (`036_parametros_planilla_2026.sql`) trae cifras investigadas en julio 2026 (UIT S/5,500, comisiones AFP por fondo, tope asegurable Q3 2026, Renta 4ta 8%/S/1,500) marcadas explicitamente como punto de partida a verificar, no como fuente oficial confirmada linea por linea.
- **Las formulas de calculo viven en TypeScript, no en SQL** (`src/lib/rrhh/planilla/calculo.ts`, funciones puras sin IO, testeables) -- mismo criterio que IGV/detraccion (`src/lib/proyectos/impuestos.ts`) y el date-walking de periodos: los procedimientos solo persisten el resultado ya calculado (`SP_RRHH_PLANILLA_DETALLE_AGREGAR` recibe los montos hechos, igual que `SP_PAGO_RECURRENTE_INSTANCIA_AGREGAR`). `calcularAportePension` (AFP topado al maximo asegurable + comision del fondo elegido + prima de seguro, u ONP flat 13%), `calcularEssalud` (costo del empleador, **no** resta el neto del colaborador), `calcularRetencionRenta4ta` (8% si el recibo supera el umbral, 0 si el locador tiene `SUSPENSION_RETENCION_4TA_HASTA` vigente), y `calcularRenta5taMensual` (proyeccion anual recalculada cada mes con lo ya acumulado en `RRHH_PLANILLA_DETALLE` del propio año -- 7 UIT de deduccion + tramos progresivos, `retencionMes = (impuesto anual proyectado - lo ya retenido este año) / meses restantes`).
  - **Alcance v1 de Renta 5ta, a confirmar con contable antes de usarla con sueldos reales**: fiel a la forma de la formula SUNAT pero sin los checkpoints de recalculo de junio/julio y noviembre/diciembre del Art. 40 del Reglamento LIR, y sin gratificaciones (no existe ese `CONCEPTO_REMUNERATIVO` hoy, quedan fuera de este calculo).
- **Pension/suspension son datos de la PERSONA, no del contrato** (`RRHH_EMPLEADO.ID_SISTEMA_PENSION`/`ID_AFP_FONDO`/`SUSPENSION_RETENCION_4TA_HASTA`, `038_rrhh_planilla_pension_empleado.sql`), editables desde `/rrhh/directorio/[idUsuario]` junto al resto de la ficha (`actualizarEmpleadoAction`). La suspension de retencion de 4ta se modela como **fecha de vencimiento** (vigente si `HOY <= SUSPENSION_RETENCION_4TA_HASTA`) en vez de un booleano manual -- se autoexpira, no depende de que alguien se acuerde de desmarcarla cada año. Si a un colaborador de planilla le falta configurar su sistema de pension, el detalle de su boleta lo avisa con un link directo a su ficha y **bloquea el boton "Emitir"** hasta que se complete (no falla en silencio).
- **"AFP/EsSalud pagados" es un control por colaborador, independiente de si ya se pago el neto** (`RRHH_PLANILLA_DETALLE.AFP_ESSALUD_PAGADO`, `SP_RRHH_PLANILLA_DETALLE_MARCAR_PAGADO`/`_MASIVO`): en la practica estos aportes se remiten a SUNAT en un solo PDT/PLAME mensual, pero el check queda por fila para poder corregir a un colaborador puntual sin afectar al resto -- con un boton "Marcar todos como pagados" a nivel de la planilla completa para el caso comun. No esta bloqueado por el estado de emision (se puede marcar dias despues de emitir las boletas).
- **Emision = generar PDF + guardarlo + bloquear edicion**, mismo orden que la firma de contratos (primero el archivo, recien despues se persiste la ruta): `generar-boleta-pdf.ts` (5ta, ingresos/descuentos/neto + nota de EsSalud como costo del empleador que no afecta el neto) y `generar-recibo-honorarios-pdf.ts` (4ta, bruto/retencion o nota de suspension vigente/neto en letras) reusan integramente `PdfWriter`, `cargarLogoEmpresa()` (el logo que subio Super Admin en `/administracion/empresa`) y la constante `EMPLEADOR` -- cero codigo de PDF nuevo, solo los datos. `SP_RRHH_PLANILLA_DETALLE_ACTUALIZAR_MONTOS` es no-op silencioso una vez `EMITIDA` (mismo criterio que `SP_RRHH_CONTRATO_PERIODO_PAGO_ACTUALIZAR`). `generar-resumen-planilla-pdf.ts` es la excepcion: se regenera al vuelo en cada descarga (`GET /api/rrhh/planilla/[idPlanillaMensual]/resumen`), no se persiste, porque es un agregado de solo lectura sobre numeros ya cerrados, no un documento legal por persona.
- **UI** (`/rrhh/planilla`): listado de corridas mensuales + boton "Generar planilla de [mes]" (idempotente, seguro reintentar); `/rrhh/planilla/[id]` la grilla del mes con bruto/descuentos/neto/estado/aportes pagados por colaborador, "Emitir planilla completa" y "Descargar resumen"; `/rrhh/planilla/[id]/[idDetalle]` el detalle por colaborador (misma logica de branching por regimen que `rrhh/contratos/[id]/page.tsx`) con montos editables antes de emitir, boton "Recalcular con tasas vigentes", y link a la boleta/RxH ya emitida.

## Cuentas (Facturacion)

- **`/facturacion/cuentas`** (area FACTURACION: `FACTURACION_JEFATURA` con `ADMIN`, `FACTURACION_ASISTENTE` con `ESCRITURA`): catalogo de cuentas de la empresa (`CUENTA_EMPRESA`) por `TIPO_CUENTA` — `BANCARIA` (soles/dolares por banco, banco tomado del mismo catalogo `TIPO_MAESTRO='BANCO'` que usa la firma de contratos), `DETRACCIONES` (igual que bancaria, sin reglas especiales), `IGV_FAVOR`/`RENTA_FAVOR` (solo saldo, sin banco ni numero de cuenta — son posiciones a favor frente a SUNAT, no cuentas bancarias). El formulario de alta oculta banco/moneda/numero de cuenta cuando el tipo no los necesita.
- **Libro de movimientos** (`CUENTA_MOVIMIENTO`, uno por cuenta, desde su detalle): cada movimiento es `INGRESO` o `EGRESO`, con fecha/monto/concepto. El saldo (`CUENTA_EMPRESA.SALDO_ACTUAL`) nunca se recibe del cliente — `SP_CUENTA_MOVIMIENTO_REGISTRAR` lo recalcula el mismo dentro de una transaccion con `SELECT ... FOR UPDATE` sobre la fila de la cuenta, para que dos movimientos concurrentes no lean el mismo saldo de partida. Solo se puede eliminar el movimiento **mas reciente** de una cuenta (`SP_CUENTA_MOVIMIENTO_ELIMINAR`, no-op silencioso si no lo es) porque cada `SALDO_RESULTANTE` depende del anterior.
- **Vinculo a otros modulos**: `TIPO_REFERENCIA`/`ID_REFERENCIA` en `CUENTA_MOVIMIENTO` es una referencia generica sin FK (a proposito). Se usa `TIPO_REFERENCIA='RRHH_CONTRATO'` (pago de un contrato), `'PASIVO_CUOTA'` (pago de una cuota de un pasivo) y `'COMPRA'` (pago de una compra) — ver seccion "Pasivos y Compras (Facturacion)". El modulo de tareas/Clockify **todavia no existe** — cuando se construya, se conectara del mismo modo (nuevo valor de `TIPO_REFERENCIA`), sin cambios de esquema. `SP_CUENTA_MOVIMIENTO_LISTAR_POR_REFERENCIA(tipoReferencia, idReferencia)` trae el historial de pagos de un origen puntual sin escanear el libro completo de una cuenta (indice `IX_MOVIMIENTO_REFERENCIA`).

## Pasivos y Compras (Facturacion)

- **`/facturacion/pasivos`** (misma area FACTURACION, app independiente `PASIVOS_EMPRESA` — mismo criterio que RRHH con `RRHH_DIRECTORIO`/`RRHH_CONTRATOS`, un area aloja varias apps con permisos separados): deudas, prestamos, lineas de credito y letras protestadas (`PASIVO`) con su plan de cuotas (`PASIVO_CUOTA`). Las cuotas se agregan una por una desde el detalle (sin generador automatico de cronograma).
  - **Acreedor estructurado** (`ID_PROVEEDOR`/`ID_CONTACTO`/`ID_USUARIO` en `PASIVO`, mismo criterio que la persona en "Mano de obra" de Proyectos): se elige, no se escribe -- exactamente una de tres fuentes: un `PROVEEDOR` (empresa que presta servicios financieros), cualquier contacto activo del Directorio (`DIRECTORIO_CONTACTO_EXTERNO`, persona natural externa, sin restringir por tipo de relacion), o personal interno de GT (`USUARIO`, ej. alguien de gerencia que presto dinero personalmente a la empresa -- mismo origen que usa el Directorio Corporativo de empleados). `SP_PASIVO_CREAR`/`SP_PASIVO_ACTUALIZAR` hacen no-op silencioso si viene mas de una fuente o ninguna (`SelectorAcreedorPasivo.tsx`, toggle de 3 opciones, mismo patron que `SelectorPersonaManoObra.tsx`). El resto de la app (lista, plan de pagos, PDF, `CuotaFilaAcciones`) sigue leyendo un campo `ACREEDOR` de texto plano — ahora calculado en cada SP con `COALESCE(proveedor.RAZON_SOCIAL, CONCAT(contacto.NOMBRES, ' ', contacto.APELLIDOS), CONCAT(usuario.NOMBRES, ' ', usuario.APELLIDOS))` en vez de guardado literal, para no tocar esas pantallas.
    - **`FINANCIA_DESCRIPCION`** (`SP_PASIVO_LISTAR`/`LISTAR_POR_PROYECTO`/`OBTENER`): mostrar solo `TIPO_REFERENCIA #ID_REFERENCIA` (ej. "PROYECTO_COSTO_MANO_OBRA #21") no decia nada util sin entrar a esa otra pantalla -- este campo resuelve, con un `CASE p.TIPO_REFERENCIA` y una subquery correlacionada por cada uno de los 4 valores posibles (mismos que usa `FinanciarConPrestamoFila.tsx`: `COMPRA`, `RRHH_CONTRATO_PERIODO_PAGO`, `RRHH_CONTRATO_HORAS`, `PROYECTO_COSTO_MANO_OBRA`), un texto legible: que compra, el sueldo/honorario de quien y que periodo, las horas de quien y que periodo, o la mano de obra manual de quien y que periodo -- mismas etiquetas que ya usa `SP_PROYECTO_MOVIMIENTO_LISTAR` para sus `CONCEPTO`. `NULL` para un pasivo normal sin financiar nada puntual. Se duplica el mismo `CASE` en las 3 procedures en vez de una `FUNCTION` compartida -- mismo criterio de "solo procedures" del resto del sistema, y evita el riesgo de `log_bin_trust_function_creators` al crear funciones en MySQL. Se muestra como columna "Financia" en `/facturacion/pasivos`, en la seccion "Pasivos" del detalle de un proyecto, y reemplaza el `TIPO_REFERENCIA #ID_REFERENCIA` crudo en el detalle de un pasivo (con ese crudo como fallback si por lo que sea la fila referenciada ya no existe). El campo `DESCRIPCION` (motivo libre del pasivo) tambien se agrego a la vista resumen del detalle -- antes solo vivia en el formulario de edicion, mas abajo de la pantalla.
  - **Pagar una cuota** es un flujo de dos pasos desde la capa de aplicacion (no una sola SP atomica): primero `registrarMovimientoCuenta` (`tipoReferencia='PASIVO_CUOTA'`), luego `SP_PASIVO_CUOTA_MARCAR_PAGADA` con el `ID_MOVIMIENTO` resultante — MySQL no anida transacciones de verdad, asi que encadenar dos SPs que abren su propia transaccion no es seguro. Mismo nivel de riesgo que ya acepta el flujo de firma de contratos (varios pasos sin rollback entre si). Acepta cuotas `PENDIENTE` o `PROTESTADA` (una letra protestada igual se puede terminar pagando); si ya no quedan cuotas pendientes/protestadas, el pasivo pasa solo a `CANCELADO`.
  - **Protestar** una cuota (`SP_PASIVO_CUOTA_PROTESTAR`) es un estado sobre la cuota (`PROTESTADA` + motivo + fecha) — no una entidad legal aparte, y no genera movimiento (no se pago). **Anular** una cuota (`SP_PASIVO_CUOTA_ANULAR`) es para condonaciones/castigos que no pasan por caja, distinto de protestar. Una cuota solo se puede `DELETE` de verdad mientras sigue `PENDIENTE`.
  - **Anular un pasivo entero** (boton "Anular" en el detalle, `AnularPasivoBoton.tsx` — expande un campo de texto inline igual que "Protestar" en `CuotaFilaAcciones.tsx`) exige una **justificacion obligatoria** (`MOTIVO_ANULACION`/`FECHA_ANULACION`/`USUARIO_ANULACION`, `037_pasivo_anulacion.sql`), igual de no-negociable en la app (`anularPasivoAction` corta si falta) como en el motivo de un protesto. `USUARIO_ANULACION` es una columna propia, separada de `USUARIO_MODIFICACION` -- si se comparte, una edicion posterior del pasivo (el formulario de edicion sigue disponible aunque ya este `ANULADO`) pisaria silenciosamente el rastro de quien lo anulo. `SP_PASIVO_LISTAR`/`LISTAR_POR_PROYECTO`/`OBTENER` resuelven `USUARIO_ANULACION` a nombre (`ANULADO_POR`, mismo patron `LEFT JOIN USUARIO` que ya usa `ACREEDOR`) para mostrar "quien, cuando y por que" -- en `/facturacion/pasivos` como `title` nativo (tooltip del navegador) sobre el badge de Estado, y como filas explicitas en el detalle. Solo se puede anular si ninguna cuota fue pagada todavia (mismo guard de antes). Para que la anulacion no deje una **carga de pasivos fantasma**, `SP_PASIVO_ANULAR` ahora hace tres cosas en cascada, no solo cambiar el estado del pasivo: (1) anula todas sus cuotas `PENDIENTE`/`PROTESTADA` (mismo estado `ANULADA` que ya usa `SP_PASIVO_CUOTA_ANULAR`) — sin esto seguian apareciendo como deuda viva en Plan de pagos/Cuentas por pagar/alertas de vencimiento, porque `SP_PASIVO_CUOTA_LISTAR_PENDIENTES` solo mira el estado de la cuota, no el del pasivo padre; (2) si el pasivo financiaba una `COMPRA` (`TIPO_REFERENCIA='COMPRA'`), recalcula `COMPRA.ID_ESTADO_COMPRA` con el mismo bloque que `SP_PASIVO_CREAR` usa al crear -- el aporte de este pasivo ya no cuenta (mismo filtro `ep.CODIGO != 'ANULADO'`), asi que una compra que estaba `PAGADA` gracias a este financiamiento vuelve a `PARCIAL`/`PENDIENTE_PAGO`; (3) `anularPasivoAction` revalida tambien la pagina del proyecto (`PASIVO.ID_PROYECTO`) cuando aplica, ademas de la lista de pasivos, el detalle, Plan de pagos y Cuentas por pagar -- los buckets de Costeo (`PASIVO_GENERADO` y los `*_PAGADO` que financian una fila puntual) ya excluian `ANULADO` de por si, pero sin este revalidate la pagina del proyecto seguia mostrando el numero cacheado de antes de anular.
- **Plan de pagos** (`/facturacion/pasivos/plan-de-pagos`, tambien accesible desde el detalle de cada cuenta via "Ver plan de pagos"): todas las cuotas pendientes/protestadas de todos los pasivos, agrupadas por la cuenta que las pagaria, ordenadas por vencimiento, con el saldo de esa cuenta restandose cuota a cuota (calculo en la app sobre una sola consulta — mismo patron que las alertas de `/rrhh/contratos`) para marcar en rojo las que dejarian la cuenta en negativo. Cuotas sin cuenta asignada quedan en un bloque aparte. Boton "Descargar PDF" (`GET /api/pasivos/plan-de-pagos/pdf`) reutiliza `PdfWriter` (`src/lib/rrhh/pdf-writer.ts`, generico pese al nombre del archivo). Alcance v1: solo considera `PASIVO_CUOTA`, no `COMPRA` (por eso `COMPRA` ya tiene una `FECHA_VENCIMIENTO` opcional desde ahora, para no migrar de nuevo despues).
- **`/facturacion/compras`** (app independiente `COMPRAS_EMPRESA`): catalogo de `PROVEEDOR` (RUC, razon social, contacto — tabla propia, no fila de `MAESTRO_MAESTRO`, necesita mas campos de los que ese catalogo soporta; `ES_PERSONA_NATURAL` marca los que son freelance/tecnico independiente en vez de empresa, editable desde su ficha — es la bolsa que usa "Mano de obra" en Proyectos, ver mas abajo) y `COMPRA` con pagos parciales (`COMPRA_PAGO`). `SP_COMPRA_PAGO_REGISTRAR` recalcula `ID_ESTADO_COMPRA` (`PENDIENTE_PAGO`/`PARCIAL`/`PAGADA`) segun cuanto se ha pagado en total. Mismo flujo de dos pasos que Pasivos: `registrarMovimientoCuenta` (`tipoReferencia='COMPRA'`) primero, `SP_COMPRA_PAGO_REGISTRAR` despues. Cada proveedor tambien tiene su seccion "Contactos" — ver "Contactos externos del Directorio" mas abajo. Junto a "Registrar pago" el detalle de la compra tambien tiene "Financiar con prestamo" (`MONTO_FINANCIADO`, `030_pasivo_referencia_proyecto.sql`) -- ver "Cuentas por Pagar y Cuentas por Cobrar" mas abajo.
- **Pagos a sueldos/honorarios** (`029_rrhh_contrato_periodo_pago.sql`, reemplaza la antigua pagina `/facturacion/compras/pagos-contratos`): no es un motor de planillas (no calcula AFP/ONP/impuestos). `PLANILLA_*`/`LOCADOR MENSUAL`/`POR_JORNADA`/`POR_PROYECTO` ya no se pagan con un boton unico que paga "el contrato" sin memoria de periodo -- ahora, en la seccion "Pagos" del detalle del contrato (`/rrhh/contratos/[id]`), cada periodo (`RRHH_CONTRATO_PERIODO_PAGO`) se paga por separado, igual que ya funcionaba `RRHH_CONTRATO_HORAS`. `LOCADOR POR_HORA` sigue sin pasar por aqui, tiene su propio mecanismo (ver abajo).
  - **Generar periodos pendientes** (`src/lib/rrhh/periodos-pago.ts`, boton en la seccion "Pagos"): en vez de escribir "JUNIO 2026" a mano cada vez, calcula en la app un periodo por cada mes calendario entre `FECHA_INICIO` del contrato y hoy (o `FECHA_FIN` si ya termino), salta los meses que ya tienen periodo, y llama a `SP_RRHH_CONTRATO_PERIODO_PAGO_AGREGAR` una vez por mes faltante con el monto sugerido (suma de conceptos para planilla, `TARIFA` para locador). Parsea las fechas con slice de texto (`"YYYY-MM-DD"`), no `new Date(string)`, para no correr el mes por el desfase UTC-5 de Peru. Si un mes puntual necesita otro monto (bono, descuento), se corrige despues con "Editar" (`SP_RRHH_CONTRATO_PERIODO_PAGO_ACTUALIZAR`, no-op silencioso si el periodo ya esta pagado o financiado) sin tocar el resto. Un periodo suelto fuera del calendario mensual (ej. "BONO EXTRAORDINARIO") se sigue pudiendo agregar a mano desde el desplegable de abajo.
  - **Pago de horas** (seccion "Horas registradas" en `/rrhh/contratos/[id]`, solo locador `POR_HORA`): unico mecanismo de pago para este tipo de contrato. Cada periodo de horas (`RRHH_CONTRATO_HORAS`) se marca pagado individualmente (`FECHA_PAGO`/`ID_MOVIMIENTO`, agregados en `027_mano_obra_pago.sql`) con el mismo flujo de dos pasos que un pago de compra: `registrarMovimientoCuenta` (`tipoReferencia='RRHH_CONTRATO_HORAS'`) y luego `SP_RRHH_CONTRATO_HORAS_MARCAR_PAGADA` (no-op silencioso si ese periodo ya estaba pagado) -- `PagarHorasContratoFila.tsx`.
  - **Financiar con prestamo en vez de pagar con caja** (`030_pasivo_referencia_proyecto.sql`): tanto un periodo de sueldo como una hora de locador (y una compra, y una asignacion de mano de obra de Proyectos) se pueden "pagar" creando un `PASIVO` nuevo en vez de sacar la plata de una cuenta -- ver seccion "Cuentas por Pagar y Cuentas por Cobrar" mas abajo para el detalle completo del mecanismo.

## Proyectos y Servicios (Facturacion)

- **`/facturacion/proyectos`** (app independiente `PROYECTOS_EMPRESA`, misma area FACTURACION): junta tres fuentes de costo que antes vivian separadas — compras, mano de obra por horas de locador y una asignacion manual de mano de obra — mas un libro de ingresos, para dar costo/margen de un `PROYECTO` (cubre tanto "proyecto" como "servicio" via `TIPO_PROYECTO`) a hoy y al cierre.
  - **Cliente** (`/facturacion/proyectos/clientes`, catalogo `CLIENTE` — RUC/razon social/contacto, calco de `PROVEEDOR`): un proyecto se elige de este catalogo (`PROYECTO.ID_CLIENTE`) en vez de tipear el nombre libremente (evita duplicados tipo "ABC S.A.C." vs "abc sac"), o se marca explicitamente como **"Proyecto interno (GT)"** (`ES_INTERNO=1`, sin cliente externo) — la casilla en el formulario oculta el selector de cliente cuando esta marcada; `SP_PROYECTO_CREAR`/`ACTUALIZAR` fuerzan `ID_CLIENTE=NULL` si `ES_INTERNO=1` sin importar lo que llegue del formulario.
  - **Contactos** (seccion "Contactos" en el detalle de cada cliente): ver "Contactos externos del Directorio" mas abajo — la tabla es compartida con Proveedores y Socios comerciales.
  - **Costo de compras**: cualquier `COMPRA` puede etiquetarse opcionalmente a un proyecto (`COMPRA.ID_PROYECTO`, selector en el formulario de nueva compra). Se cuenta el monto **comprometido** (`MONTO_TOTAL`, sin importar si ya se pago) porque una compra `PENDIENTE_PAGO` ya es costo real del proyecto — el detalle tambien muestra el monto efectivamente pagado aparte, sin perder esa distincion.
  - **Nombre de proyecto = Proyecto/Servicio real**: el "nombre de proyecto" de un contrato LOCADOR (los dos lugares: `RRHH_CONTRATO.ID_PROYECTO` para tarifa unica, `RRHH_CONTRATO_PROYECTO.ID_PROYECTO` para por hora) ya no es texto libre — se elige entre los `PROYECTO`/servicio existentes, para que el costeo sea trazable de verdad cuando aplica. Es **obligatorio solo para `POR_PROYECTO`** (pago fijo 1:1 con un entregable, se suma solo al costeo de ese proyecto) y para `POR_HORA` (cada fila de `RRHH_CONTRATO_PROYECTO` es por definicion un enlace a un proyecto). Para `MENSUAL`/`POR_JORNADA` es **opcional**: un locador de honorario recurrente puede ser transversal a varios proyectos a la vez (ej. gerencia, soporte general) en vez de pertenecer a uno solo — `SP_RRHH_CONTRATO_CREAR` hace no-op silencioso solo si falta el proyecto en `POR_PROYECTO`. El PDF del contrato sigue usando el placeholder `{{NOMBRE_PROYECTO}}`, ahora resuelto via `JOIN PROYECTO` en vez de guardado literal (mismo truco de alias que el `ACREEDOR` de Pasivos).
  - **Costo de mano de obra por horas**: el "proyecto" que ya existe dentro de un contrato LOCADOR POR_HORA (`RRHH_CONTRATO_PROYECTO`) esta enlazado al Proyecto global — a partir de ahi sus horas cargadas (`RRHH_CONTRATO_HORAS.MONTO_CALCULADO`) cuentan solas en el costeo, sin duplicar nada. La seccion **"Mano de obra (horas)"** del detalle del proyecto (`SP_PROYECTO_MANO_OBRA_HORAS_LISTAR`) desglosa ese total por persona/periodo, y cada fila tambien se puede **pagar o financiar con prestamo directamente ahi** (`PagarHorasContratoFila`/`FinanciarConPrestamoFila`, mismos componentes que ya usaba `/rrhh/contratos/[id]`) — `PagarHorasContratoFila` se generalizo a recibir campos sueltos en vez de un `ContratoHorasRow` completo para poder reusarse desde ambas pantallas, y `pagarHorasContratoAction` gano un `idProyecto` opcional para revalidar tambien la pagina de Proyectos cuando el pago se dispara desde ahi (mismo criterio que `rutaOrigen` ya usa `financiarConPrestamoAction`).
  - **Costo de mano de obra por tarifa unica**: un contrato LOCADOR `POR_PROYECTO` (pago fijo por un entregable, no recurrente, unico tipo que exige proyecto obligatoriamente) suma su `TARIFA` una sola vez y automaticamente al costeo del `PROYECTO` que enlaza (`COSTO_MANO_OBRA_TARIFA_UNICA`, mismo patron de subquery `COALESCE(SUM(...),0)` que los demas buckets) — a diferencia de `MENSUAL`/`POR_JORNADA` (montos recurrentes, proyecto opcional porque pueden ser transversales a varios proyectos), que **no** se suman solos aunque tengan un proyecto enlazado, porque no hay mecanismo de devengo por periodo; ese costo se sigue cargando a mano, periodo a periodo, desde "Mano de obra (asignacion manual)" (que ya soporta enlazar `ID_CONTRATO` y, al ser manual, admite repartir el mismo contrato entre varios proyectos).
  - **Costo de mano de obra manual** (`PROYECTO_COSTO_MANO_OBRA`): para planilla y cualquier tipo de pago que no se registra por hora ni por tarifa unica — una asignacion por periodo (monto, periodo libre tipo "Mayo 2026", moneda propia — igual que `COMPRA`, no se fuerza la del proyecto), cargada a mano desde el detalle del proyecto. Ledger de solo insertar/borrar, igual que `RRHH_CONTRATO_HORAS`/`COMPRA_PAGO`. La persona **se elige, no se escribe**: es exactamente una de dos fuentes — un contrato de RRHH (`ID_CONTRATO`) o un proveedor marcado `ES_PERSONA_NATURAL=1` (`ID_PROVEEDOR`, freelance/tecnico independiente que factura como proveedor) — `SP_PROYECTO_COSTO_MANO_OBRA_AGREGAR` hace no-op silencioso si vienen las dos, ninguna, o un proveedor que no esta marcado persona natural (`AgregarCostoManoObraForm.tsx`, toggle entre los dos `ComboBusqueda`).
    - **Jalar periodo/monto desde un contrato con periodos ya cargados** (`AgregarCostoManoObraForm.tsx`): si el contrato de RRHH elegido ya tiene datos cargados, aparece un selector opcional que elegir uno precarga los campos Periodo y Monto (siguen editables a mano). Dos fuentes, mutuamente excluyentes segun el tipo de contrato:
      - `SP_RRHH_CONTRATO_PERIODO_PAGO_LISTAR_TODOS` (cross-contrato) para PLANILLA/LOCADOR `MENSUAL`/`POR_JORNADA`/`POR_PROYECTO` -- periodos de sueldo/honorario ya generados (ver "Pagos a sueldos/honorarios" mas abajo), `"JUNIO 2026 - S/ 1200"` con nota `(pagado)`/`(financiado)` si aplica.
      - `SP_RRHH_CONTRATO_HORAS_LISTAR_TODOS` (cross-contrato, nuevo) para LOCADOR `POR_HORA` -- este tipo no genera `RRHH_CONTRATO_PERIODO_PAGO` (tiene su propio mecanismo de pago por horas), asi que sin este segundo selector el picker no mostraba nada para un locador por horas aunque ya tuviera periodos con horas y tarifa cargados. Muestra las horas ya registradas de cualquier proyecto enlazado (`"JUNIO 2026 (Proyecto X) - 20h - S/ 800"`, mismas notas `(pagado)`/`(financiado)`), con `MONTO_CALCULADO` (horas × tarifa) ya resuelto.
      - En ambos casos es solo una sugerencia de arranque, sin ningun enlace persistido entre la fila de `PROYECTO_COSTO_MANO_OBRA` y el origen — a proposito, porque el mismo periodo/horas puede ser transversal a varios proyectos (ver "MENSUAL/POR_JORNADA... opcional" mas arriba), y el monto que aplica a este proyecto puede ser solo una parte del total. Elegir un **periodo de sueldo/honorario** fuerza la Moneda a soles (`RRHH_CONTRATO_PERIODO_PAGO` no tiene columna de moneda propia, siempre esta en soles); elegir **horas** en cambio trae la moneda/TC reales con las que se cargo esa fila (`RRHH_CONTRATO_PROYECTO.ID_MONEDA`/`TIPO_CAMBIO`, ver "Tipo de cambio (TC) al mezclar monedas" mas abajo) — en ambos casos el combo de Moneda sigue editable por si de verdad corresponde otra.
  - **Guard contra doble conteo**: si un contrato ya esta enlazado por horas a un proyecto, o ya cuenta solo como tarifa unica de ese mismo proyecto, no se le puede agregar ademas una asignacion manual para ese mismo proyecto (y viceversa) — no-op silencioso en el procedimiento correspondiente, mismo estilo que el resto del sistema (no se usa `SIGNAL` en ningun procedimiento).
  - **Cuanto de la mano de obra ya se pago** (`027_mano_obra_pago.sql`): los tres buckets de mano de obra son "presupuesto" (comprometido), igual que `COSTO_COMPRAS` -- para saber cuanto ya se pago y cuanto sigue pendiente, cada fuente se marca pagada a nivel de la fila especifica que ya es 1:1 con un solo proyecto (nunca a nivel de todo el contrato, que si podria tocar mas de un proyecto): `PROYECTO_COSTO_MANO_OBRA` y `RRHH_CONTRATO_HORAS` ganan `FECHA_PAGO`/`ID_MOVIMIENTO` (mismo patron que `PASIVO_CUOTA`, sin tabla hija porque a diferencia de una compra esto no se paga en cuotas parciales) y se marcan pagadas con `SP_PROYECTO_COSTO_MANO_OBRA_MARCAR_PAGADA`/`SP_RRHH_CONTRATO_HORAS_MARCAR_PAGADA` (botón "Pagar" por fila, `PagarCostoManoObraFila.tsx`/`PagarHorasContratoFila.tsx`, mismo flujo de dos pasos que `registrarPagoCompraAction`). La tarifa unica no necesita columnas nuevas -- como un contrato `POR_PROYECTO` ya es 1:1 con su proyecto, reutiliza los `CUENTA_MOVIMIENTO` que "Pagos a sueldos/honorarios" ya crea. `SP_PROYECTO_OBTENER` expone los tres `_PAGADO` (`COSTO_MANO_OBRA_MANUAL_PAGADO`/`_HORAS_PAGADO`/`_TARIFA_UNICA_PAGADO`, solo en el detalle, mismo criterio que `COSTO_COMPRAS_PAGADO`), y el detalle del proyecto muestra un total "Mano de obra - pendiente de pago" (comprometido − pagado de los tres).
  - **Pasivo generado por el proyecto** (`030_pasivo_referencia_proyecto.sql`, `PROYECTO.PASIVO_GENERADO` en `SP_PROYECTO_LISTAR`/`OBTENER`): junto a "Pagar", cada fila pendiente de mano de obra tiene tambien "Financiar con prestamo" (`FinanciarConPrestamoFila.tsx`) -- crea un `PASIVO` nuevo que reemplaza el pago (no se mueve caja), enlazado directo a esa asignacion/hora y al proyecto (`PASIVO.ID_PROYECTO`). El detalle del proyecto suma todos los pasivos que lo tienen como `ID_PROYECTO`, para ver de un vistazo cuanta deuda genero financiar sus costos en vez de pagarlos con caja de la empresa. `PASIVO_GENERADO` tambien sale en el dashboard (`/facturacion/proyectos`, cada tarjeta muestra una nota ambar si es mayor a cero) — antes solo vivia en `SP_PROYECTO_OBTENER`, se replico el mismo subquery en `SP_PROYECTO_LISTAR` (moviendo el campo a `ProyectoCosteoBase` en `types/db.ts`, compartido por `ProyectoListadoRow`/`ProyectoDetalleRow`).
    - **Seccion "Pasivos" en el detalle del proyecto** (`SP_PASIVO_LISTAR_POR_PROYECTO`, mismo SELECT que `SP_PASIVO_LISTAR` pero filtrado por `ID_PROYECTO` e incluyendo anulados/cancelados para no perder el historial): tabla de solo lectura (acreedor, tipo, monto total, pendiente, estado) — cada fila enlaza a `/facturacion/pasivos/[id]`, que es donde ya vive el flujo completo de pagar/protestar/anular una cuota (`CuotaFilaAcciones.tsx`) — se opto por enlazar en vez de duplicar esas acciones aca, mismo criterio que "Compras vinculadas" ya usaba (la pantalla dueña del dato es quien expone sus acciones, el resto solo enlaza).
    - Ver "Cuentas por Pagar y Cuentas por Cobrar" mas abajo para el mecanismo completo de financiar con prestamo (tambien aplica a compras y sueldos/honorarios).
  - **Tipo de cambio (TC) al mezclar monedas** (`031_tipo_cambio_proyecto.sql`/`033_ingreso_moneda.sql`): `COMPRA`, `PROYECTO_COSTO_MANO_OBRA`, `PASIVO` (cuando esta enlazado a un proyecto via `ID_PROYECTO`) y `PROYECTO_INGRESO` eligen su propia moneda independiente de la del proyecto -- cada una tiene `TIPO_CAMBIO DECIMAL(10,4)`, obligatorio SOLO si la fila queda en una moneda distinta a la del proyecto que la usa (no-op silencioso si falta, mismo estilo del resto del sistema), y queda fijo para siempre una vez capturado, igual que `PASIVO_CUOTA.MONTO`/`PROYECTO_HITO.MONTO` -- no se recalcula si el TC del dia cambia despues.
    - **`TIPO_CAMBIO` siempre es "soles por dolar"** (la unica forma en que alguien en Peru tipea un TC, mismo criterio que el TC oficial SUNAT que ya consume este sistema -- ver "Tipo de Cambio" mas abajo) -- **no** "cuantas unidades de la moneda del proyecto equivalen a 1 de la fila" (asi se diseño originalmente y era el bug: multiplicaba siempre, sin importar el sentido de la conversion, inflando de mas cualquier gasto en soles cargado a un proyecto en dolares). La formula correcta depende de cual lado es el dolar: `CASE WHEN ID_MONEDA = proyecto.ID_MONEDA THEN MONTO WHEN TIPO_CAMBIO IS NULL THEN MONTO WHEN ID_MONEDA = id_moneda_usd THEN MONTO * TIPO_CAMBIO ELSE MONTO / TIPO_CAMBIO END` -- multiplicar convierte dolares a soles, dividir convierte soles a dolares. Todos los buckets de costeo (`SP_PROYECTO_LISTAR`/`OBTENER`) y `SP_PROYECTO_MOVIMIENTO_LISTAR` usan esta misma formula (con `id_moneda_usd` resuelto una vez por `MAESTRO_MAESTRO WHERE TIPO_MAESTRO='MONEDA' AND CODIGO='USD'`).
    - En el ledger de Movimientos, cuando hay conversion, el monto y la moneda originales quedan anotados en el `CONCEPTO` de la fila para que sea trazable. Las filas se muestran con "TC x.xxxx" debajo del monto en las tablas de detalle (Mano de obra manual, Compras vinculadas) y como dato aparte en el detalle de Compra/Pasivo.
    - **RRHH (tarifa unica y por hora) tambien tiene moneda propia** (`034_rrhh_contrato_moneda.sql`): antes ninguna de las dos tablas tenia columna de moneda, asi que un locador cobrando en soles en un proyecto en dolares se sumaba tal cual al costeo, como si ya fuera dolares -- bug real reportado con un locador POR_HORA a S/15/hora, cuyo costo salia mal en un proyecto en USD. `RRHH_CONTRATO.ID_MONEDA`/`TIPO_CAMBIO` cubre la tarifa unica (`POR_PROYECTO`, un solo proyecto por contrato via `RRHH_CONTRATO.ID_PROYECTO`, asi que la moneda vive junto a la tarifa en la misma fila). `RRHH_CONTRATO_PROYECTO.ID_MONEDA`/`TIPO_CAMBIO` (NOT NULL, toda fila tiene `TARIFA_HORA`) cubre `POR_HORA` **independiente por cada proyecto enlazado** -- decision explicita del usuario, ya que un locador por hora puede facturarle a varios proyectos a la vez, cada uno en su propia moneda. Misma regla de siempre: `TIPO_CAMBIO` obligatorio SOLO si la moneda elegida difiere de la del proyecto enlazado (no-op silencioso si falta), y los cuatro buckets afectados (`COSTO_MANO_OBRA_HORAS`/`_PAGADO`, `COSTO_MANO_OBRA_TARIFA_UNICA`/`_PAGADO` en `SP_PROYECTO_LISTAR`/`OBTENER`, mas `GASTO_MANO_OBRA_HORAS`/`GASTO_MANO_OBRA_TARIFA_UNICA` en `SP_PROYECTO_MOVIMIENTO_LISTAR`) usan la misma formula `CASE` que el resto de este apartado. En `AgregarCostoManoObraForm.tsx`, jalar una fila de horas ya cargada ahora trae su moneda/TC reales en vez de forzar siempre soles (jalar un periodo de sueldo si sigue forzando soles -- `RRHH_CONTRATO_PERIODO_PAGO` no tiene columna de moneda, ese alcance no cambio).
  - **Ingresos** (`PROYECTO_INGRESO`): varios registros con fecha/monto/concepto por proyecto (anticipos, pagos parciales, pago final) en vez de un solo campo de "monto de contrato" — sirve tanto para proyectos de pago unico como para servicios recurrentes. Sin cadena de saldo acumulado, cualquier fila se borra libremente. `ID_MOVIMIENTO` es una reconciliacion opcional con un movimiento real de Cuentas, mapeada para el futuro pero sin UI de vincular todavia.
  - **Dashboard** (`/facturacion/proyectos`): tarjeta por proyecto con barra de progreso costo-a-hoy-vs-presupuesto (se marca en rojo si se pasa del presupuesto) e ingreso-a-hoy-vs-esperado, mas margen actual (ingreso real − costo real) y margen al cierre (`INGRESO_ESPERADO` − `COSTO_PRESUPUESTADO`, los dos campos que se cargan al crear el proyecto) — sin proyeccion automatica por tendencia, son los numeros ya acordados con el cliente.
  - **Gastos** (seccion aparte en el detalle): desglosa el costo real total en sus tres fuentes (compras, mano de obra por horas, mano de obra manual) con una barra por categoria, para ver de un vistazo que pesa mas en el costo del proyecto.
  - **Movimientos** (seccion aparte en el detalle, `SP_PROYECTO_MOVIMIENTO_LISTAR`): ledger cronologico combinado de ingresos y salidas — junta `PROYECTO_INGRESO` (ingresos), `COMPRA_PAGO` de compras vinculadas (gasto), `PROYECTO_COSTO_MANO_OBRA` (gasto), `RRHH_CONTRATO_HORAS` de contratos enlazados (gasto) y `CUENTA_MOVIMIENTO` de locadores `POR_PROYECTO` enlazados (gasto, tarifa unica) en una sola tabla ordenada por fecha, con saldo acumulado calculado en la app (mismo patron que el plan de pagos de Pasivos: se ordena ascendente para acumular y se muestra descendente). Los tres gastos de mano de obra solo salen **ya pagados** (usan `FECHA_PAGO`, no la fecha en que se comprometieron) — mismo criterio que `GASTO_COMPRA`, que ya sale de `COMPRA_PAGO` (pago real) y no de cuando se creo la `COMPRA`; una asignacion/hora/tarifa unica pendiente de pago sigue sumando al costeo/Gastos como comprometido, pero no aparece aqui hasta que se pague.
  - **"Zona de riesgo" -- reset masivo por fuente** (seccion aparte al final del detalle, pide `ADMIN` en vez de `ESCRITURA`, mismo criterio que "Cerrar"/"Anular" proyecto): tres botones para limpiar de golpe una fuente completa cargada por error, sin borrar fila por fila -- "Reset ingresos" (`SP_PROYECTO_RESET_INGRESOS`, borra todo `PROYECTO_INGRESO` del proyecto salvo el que ya este enlazado a un item `COBRADO` del plan de facturacion, mismo guard que el borrado de una sola fila), "Reset compras" (`SP_PROYECTO_RESET_COMPRAS`, **desvincula** -- `COMPRA.ID_PROYECTO = NULL` -- nunca borra la compra, no existe borrado de compras en ningun lado del sistema, se tratan como registro financiero permanente) y "Reset costos laborales" (`SP_PROYECTO_RESET_COSTOS_LABORALES`, limpia las tres fuentes de mano de obra a la vez: borra `PROYECTO_COSTO_MANO_OBRA`, desvincula los contratos `LOCADOR POR_HORA` del proyecto -- lo que tambien borra sus horas cargadas, mismo comportamiento que `SP_RRHH_CONTRATO_PROYECTO_ELIMINAR` -- y desvincula los `LOCADOR POR_PROYECTO` de tarifa unica). Los tres incluyen **deliberadamente** filas ya pagadas o financiadas con un pasivo (a diferencia del resto del sistema, que en general protege lo ya pagado) -- un `PASIVO`/`CUENTA_MOVIMIENTO` ya creado nunca se borra (es deuda/caja real), solo queda con una referencia suelta (mismo criterio de "sin FK a proposito" que ya usan `TIPO_REFERENCIA`/`ID_REFERENCIA`). Los tres son procedimientos nuevos en `sp_proyecto.sql`, sin cambio de schema.
  - **Plan de facturación** (`PROYECTO_HITO`, en el detalle del proyecto): distintos esquemas de facturación de un cliente — adelanto + factura final por porcentaje, hitos (con o sin adelanto), facturación variable, o una sola factura al cierre — se modelan como items de un mismo plan, cada uno de un `TIPO_HITO_FACTURACION` (`ADELANTO`/`HITO`/`FACTURA_FINAL`/`VARIABLE`). Cada item se carga con **monto fijo o como porcentaje del `INGRESO_ESPERADO`** del proyecto (`SP_PROYECTO_HITO_AGREGAR` calcula el monto una sola vez al crearlo y lo deja fijo — no se recalcula si el ingreso esperado cambia despues, mismo criterio que `PASIVO_CUOTA.MONTO`). Tres estados: `PLANEADO` → `FACTURADO` (se emitió la factura, con N° opcional) → `COBRADO`. **Cobrar un item** es el mismo flujo de dos pasos que pagar una cuota de Pasivos: se crea el `PROYECTO_INGRESO` real (`agregarIngresoProyecto`) y con ese `ID_INGRESO` se enlaza el item (`SP_PROYECTO_HITO_MARCAR_COBRADO`) — así el dashboard sigue viendo un solo ingreso real por cobro, y el plan sabe cuál item ya se cumplió. `MONTO_PLAN_PENDIENTE` (suma de items `PLANEADO`/`FACTURADO`) se muestra junto al costeo — cuánto falta por facturar/cobrar del plan.
    - **IGV y detracción, de solo cálculo** (`src/lib/proyectos/impuestos.ts`, mismo criterio que `calcularCosteo` — matemática pura de visualización, no persiste nada ni toca `PROYECTO_HITO.MONTO`): `PROYECTO_HITO.MONTO`/`PROYECTO.INGRESO_ESPERADO` se interpretan como el monto **sin IGV** (confirmado con el usuario) — IGV 18% se suma encima (`montoConIgv = montoBase * 1.18`), y la detracción 12% (tasa fija para todos los items, Geeky Tech factura servicios bajo un solo régimen) se calcula sobre el monto **con** IGV, no sobre la base, tal como lo define SUNAT. Cada fila del Plan de facturación muestra el desglose completo (monto base, IGV, total con IGV, detracción, neto a cobrar). En Costeo, dos totales agregados: **"IGV por declarar a SUNAT"** (suma el IGV de items `FACTURADO`/`COBRADO`, en la moneda del proyecto — la obligación tributaria nace con el comprobante, no con el cobro) y **"Detracción pendiente de depósito"** (solo items `FACTURADO`, no `COBRADO` — una vez cobrado se asume que la detracción ya llegó a la cuenta de detracciones de `/facturacion/cuentas`). `PLANEADO` no suma a ninguno de los dos, todavía no existe comprobante.
      - **La detracción SIEMPRE se deposita en soles ante SUNAT**, sin importar la moneda de facturación del proyecto (asi lo exige SUNAT para operaciones en moneda extranjera) — para un proyecto en USD, `calcularImpuestosItem` convierte con el TC vigente de Ventas (`obtenerTipoCambioVigente("VENTA")`, el mismo que ya sugiere el TC al agregar un ingreso) antes de aplicar el 12%. Es un estimado con el TC de hoy, no un valor fijado — `PROYECTO_HITO` no guarda su propio TC por fila (a diferencia de `PROYECTO_INGRESO`), asi que el numero fluctua si el TC cambia despues. El "Neto a cobrar" de cada item (lo que el cliente transfiere a la cuenta normal, no a detracciones) se queda en la moneda del proyecto — solo el monto de detracción en si se fuerza a soles.
      - **"IGV pendiente de declarar" contra el saldo a favor de IGV** (seccion nueva en el detalle de la cuenta `IGV_FAVOR`, `/facturacion/cuentas/[id]`, visible solo cuando `cuenta.TIPO_CUENTA_CODIGO === 'IGV_FAVOR'`): a diferencia del "IGV por declarar a SUNAT" de Costeo (que queda en la moneda de un solo proyecto), esta vista es **cross-proyecto** (`SP_PROYECTO_HITO_LISTAR_IGV_PENDIENTE`, mismos items `FACTURADO`/`COBRADO` de TODOS los proyectos) y **siempre convierte a soles** (`calcularIgvConsolidado` en `impuestos.ts`) porque se compara contra un saldo compartido de toda la empresa que SUNAT tambien exige en soles. Muestra tres numeros: el IGV total por declarar, cuanto se aplicaría del saldo a favor (`Math.min(igvTotalSoles, SALDO_ACTUAL)`) y el IGV restante que quedaría a pagar en efectivo. **Aplicar es una accion manual con confirmacion** (`aplicarSaldoIgvFavorAction`, botón "Aplicar contra saldo a favor"): registra un `EGRESO` real en `CUENTA_MOVIMIENTO` de esa cuenta via `registrarMovimientoCuenta` (mismo mecanismo que ya usa el resto del sistema, `SALDO_ACTUAL` se recalcula solo) — el monto sugerido viene topado al saldo disponible pero sigue siendo editable, porque `PROYECTO_HITO` no tiene concepto de "periodo/declaracion" (el total mostrado es acumulado historico de todo lo facturado/cobrado, no solo lo del mes en curso) — el usuario ajusta el monto a lo que realmente corresponde declarar ese mes, mismo criterio que cualquier otro monto sugerido-pero-editable del sistema. No hay tracking de que hitos "ya se declararon" — cada aplicación es una decision manual, no una automatizacion de periodo.

## Cuentas por Pagar y Cuentas por Cobrar (Facturacion)

- **`/facturacion/cuentas-por-pagar`** (app nueva `CUENTAS_POR_PAGAR`, area FACTURACION) y **`/facturacion/cuentas-por-cobrar`** (app nueva `CUENTAS_POR_COBRAR`): dos vistas consolidadas de solo lectura + enlaces al origen — mismo criterio que ya usa "Plan de pagos" de Pasivos (lista, no re-implementa el pago) — para no tener que entrar modulo por modulo a ver que falta pagar o cobrar.
  - **Cuentas por Pagar**: junta en una sola tabla, ordenada por fecha, todo lo pendiente de las cinco fuentes: `SP_COMPRA_LISTAR_PENDIENTES`, `SP_RRHH_CONTRATO_PERIODO_PAGO_LISTAR_PENDIENTES`, `SP_RRHH_CONTRATO_HORAS_LISTAR_PENDIENTES`, `SP_PROYECTO_COSTO_MANO_OBRA_LISTAR_PENDIENTES` (nuevas las cuatro) y `SP_PASIVO_CUOTA_LISTAR_PENDIENTES` (ya existia). Las de RRHH usan el mismo aislamiento de datos sensibles que el resto del modulo (nada de DNI/direccion/banco/firma). Cada fila enlaza a su pantalla de origen (compra, contrato, proyecto o pasivo) — el pago/financiamiento en si se hace ahi, no en esta vista.
  - **Cuentas por Cobrar**: `SP_PROYECTO_HITO_LISTAR_PENDIENTES()` (nueva, cross-proyecto, mismas columnas que `SP_PROYECTO_HITO_LISTAR` + `PROYECTO_NOMBRE`) lista los items `PLANEADO`/`FACTURADO` de **todos** los proyectos a la vez. A diferencia de Cuentas por Pagar, aca si reusa el componente de accion tal cual (`HitoFilaAcciones.tsx`, el mismo que usa el detalle del proyecto) porque `ProyectoHitoPendienteRow` extiende `ProyectoHitoRow` -- "Marcar facturado"/"Cobrar" funcionan identico, sin re-implementar nada.
- **Financiar con prestamo en vez de pagar con caja** (`030_pasivo_referencia_proyecto.sql`): la pieza que hace posible todo esto. `PASIVO` gana `TIPO_REFERENCIA`/`ID_REFERENCIA` (generico, sin FK, mismo criterio que `CUENTA_MOVIMIENTO`) y `ID_PROYECTO` (directo, no derivado). Un pasivo con `TIPO_REFERENCIA='COMPRA'`/`ID_REFERENCIA=123` **es** el pago de esa compra -- no se crea ningun `CUENTA_MOVIMIENTO` ni fila de pago, la deuda nueva reemplaza directamente el pago viejo. `SP_PASIVO_CREAR` gana esos tres parametros (NULL para un pasivo normal que no financia nada puntual); cuando financia una `COMPRA`, ademas recalcula `ID_ESTADO_COMPRA` inline (mismo bloque `PAGADA`/`PARCIAL` que `SP_COMPRA_PAGO_REGISTRAR`, sumando lo pagado en efectivo + lo financiado). Las cuatro fuentes de "pendiente" (compras, periodos de sueldo, horas, mano de obra) restan tanto lo pagado en efectivo como lo financiado con pasivo para calcular cuanto sigue pendiente de verdad.
  - **`FinanciarConPrestamoFila.tsx`** (componente compartido, `src/components/facturacion/`): mismo `SelectorAcreedorPasivo` de 3 fuentes que ya usa Pasivos, mas tipo/monto/moneda/fecha origen/cuenta por defecto para las cuotas futuras. Una sola accion compartida, `financiarConPrestamoAction` (en `src/lib/actions/pasivos.ts`, requiere `PASIVOS_EMPRESA` `ESCRITURA` -- la mutacion real es siempre un INSERT en `PASIVO`), la usan las 4 pantallas con pagos pendientes (compra, periodos de sueldo, horas de locador, mano de obra manual de proyecto) en vez de 4 casi-iguales. `rutaOrigen` viaja como campo oculto del formulario para que la accion sepa que pantalla revalidar sin tener que conocer las 4 rutas de antemano.
  - **Trazabilidad a nivel de proyecto**: cuando lo financiado tiene proyecto (compra con `ID_PROYECTO`, asignacion de mano de obra, horas de locador, o un periodo de sueldo de un contrato con `ID_PROYECTO`), `FinanciarConPrestamoFila` lo pasa como `idProyecto` al crear el pasivo -- asi `PROYECTO.PASIVO_GENERADO` (`SP_PROYECTO_OBTENER`) puede sumarlo. Un prestamo general de la empresa (no ligado a nada puntual) simplemente no pasa `idProyecto`/`tipoReferencia`, igual que un `PASIVO` creado desde `/facturacion/pasivos/nuevo` hoy.

## Pagos Recurrentes (Facturacion)

- **`/facturacion/pagos-recurrentes`** (app nueva `PAGOS_RECURRENTES`, area FACTURACION, `035_pagos_recurrentes.sql`): cronograma de gastos que se repiten periodo tras periodo (alquiler, internet, software, seguros, mantenimientos...) sin cargarlos a mano cada vez. Mismo patron **plantilla + instancias generadas** que `RRHH_CONTRATO`/`RRHH_CONTRATO_PERIODO_PAGO`: `PAGO_RECURRENTE` es la configuracion (nombre, monto fijo o variable, moneda, cada cuantos meses, dia de vencimiento, fecha de inicio/fin, proyecto opcional, cuenta de pago por defecto), `PAGO_RECURRENTE_INSTANCIA` es el ledger de ocurrencias (insertar/marcar pagado/borrar, sin upsert, igual que `RRHH_CONTRATO_HORAS`/`PROYECTO_COSTO_MANO_OBRA`).
  - **Monto fijo vs variable** (`ES_VARIABLE`): fijo copia `MONTO_FIJO` a cada instancia generada; variable genera con `MONTO=0` como placeholder -- el monto real se carga despues por fila con `SP_PAGO_RECURRENTE_INSTANCIA_ACTUALIZAR` (`EditarInstanciaPagoRecurrenteFila.tsx`), mientras la instancia siga sin pagar ni financiar, antes de pagarla.
  - **"Cada cuantos meses" generico** (`INTERVALO_MESES`, `src/lib/pagos-recurrentes/generar-instancias.ts`): 1 = mensual, 3 = trimestral, 12 = anual... un solo mecanismo para todas las frecuencias, extendido de `generarPeriodosPendientes` (RRHH) que caminaba de a un mes -- este camina de a `INTERVALO_MESES`, calculando tambien la `FECHA_VENCIMIENTO` real de cada periodo con `DIA_VENCIMIENTO` clampeado al ultimo dia del mes si es mas corto (ej. 31 en febrero -> 28/29). `anioMes`/`esAnterior` se exportaron de `periodos-pago.ts` para reusarlos en vez de duplicar el parseo de fechas (siempre por slice de texto, nunca `new Date(string)`, para no correr el mes por el desfase UTC-5 de Peru).
  - **Generacion automatica diaria, sin cron real** (`src/lib/pagos-recurrentes/auto-generar.ts` -> `asegurarInstanciasGeneradasDelDia()`, llamada desde `facturacion/layout.tsx` junto a `asegurarTipoCambioDelDia()`): mismo mecanismo que el sync de TC SUNAT -- como esta app es Next.js + Server Actions sin worker en segundo plano, "automatico" se logra dejando que la primera visita del dia a **cualquier** pantalla de Facturacion (no solo `/facturacion/pagos-recurrentes`) recorra todos los `PAGO_RECURRENTE` `ACTIVO` y genere sus instancias faltantes. `PAGO_RECURRENTE_GENERACION_DIA` (`036_pago_recurrente_generacion_dia.sql`, una fila por fecha, PK) es la cache que evita repetir el recorrido en cada request del mismo dia -- calco exacto de `TIPO_CAMBIO_SUNAT_DIA` (`SP_PAGO_RECURRENTE_GENERACION_DIA_GUARDAR` usa `WHERE NOT EXISTS` para no duplicar si dos requests casi simultaneos dispararan la generacion a la vez). Las instancias generadas asi quedan con `USUARIO_CREACION = NULL`, mismo criterio que las filas automaticas de TC. El boton "Generar instancias pendientes" en el detalle de cada pago sigue existiendo como version manual/a demanda (`generarInstanciasPendientesAction`) -- fuerza un chequeo inmediato de un pago puntual sin esperar a la proxima visita del dia, mismo rol que "Actualizar TC ahora" cumple para el TC.
  - **Sin reparto automatico entre proyectos** (decision explicita): `PAGO_RECURRENTE.ID_PROYECTO` es opcional -- un gasto "administrativo/general" o transversal a varios proyectos simplemente se deja sin proyecto, o se crean pagos recurrentes separados uno por proyecto si de verdad hay que cargarlo a cada uno. Mismo criterio que usa **todo** el resto del sistema (ej. un locador mensual transversal a varios proyectos tampoco se reparte solo, se carga a mano proyecto por proyecto desde "Mano de obra").
  - **Cuenta de pago por defecto, pero editable por instancia** (`ID_CUENTA_PAGO_DEFAULT` en el padre, `ID_CUENTA_PAGO` en cada instancia): mismo patron que `PASIVO.ID_CUENTA_PAGO` vs `PASIVO_CUOTA.ID_CUENTA_PAGO` -- `SP_PAGO_RECURRENTE_INSTANCIA_AGREGAR` hereda la del padre si no se especifica una, pero cada instancia puede pagarse con otra cuenta (no todos los meses se paga necesariamente de la misma).
  - **Moneda propia + TC** (`ID_MONEDA`/`TIPO_CAMBIO` en `PAGO_RECURRENTE`, no por instancia -- la moneda de un pago recurrente no cambia mes a mes, mismo criterio que `RRHH_CONTRATO_PROYECTO`): `TIPO_CAMBIO` obligatorio SOLO si hay proyecto y su moneda es distinta a la del pago (no-op silencioso si falta, mismo estilo del resto del sistema).
  - **Pagar o financiar con prestamo**: pagar es el mismo flujo de dos pasos que el resto (`registrarMovimientoCuenta` + `SP_PAGO_RECURRENTE_INSTANCIA_MARCAR_PAGADA`, `pagarInstanciaAction`). Financiar reusa integramente `FinanciarConPrestamoFila.tsx`/`financiarConPrestamoAction` con `tipoReferencia="PAGO_RECURRENTE_INSTANCIA"` -- cero cambios a `PASIVO`, solo una rama nueva en el `CASE` de `FINANCIA_DESCRIPCION` (`SP_PASIVO_LISTAR`/`LISTAR_POR_PROYECTO`/`OBTENER`) para mostrar "Pago recurrente: {nombre} - {periodo}" en vez del crudo `TIPO_REFERENCIA #ID_REFERENCIA`.
  - **Alertas de vencimiento compartidas** (`src/components/ui/IconoAlertaVencimiento.tsx`, extraido de `/rrhh/contratos` -- primer lugar que las tuvo): mismos 3 niveles de urgencia (rojo/ambar/azul segun dias restantes) y el mismo icono con tooltip nativo, ahora reusados tambien en el listado de Pagos Recurrentes (paneles de alerta + icono por fila) sin duplicar la logica de color/dias.
  - **Impacto en Proyectos**: si un pago recurrente tiene `ID_PROYECTO`, sus instancias suman a `COSTO_PAGOS_RECURRENTES`/`COSTO_PAGOS_RECURRENTES_PAGADO` (`SP_PROYECTO_LISTAR`/`OBTENER`, mismo patron `CASE`/`COALESCE(SUM(...))` de conversion de moneda que el resto de buckets) y a `costoReal` en `calcularCosteo` (asi que si afecta el margen, no solo se muestra aparte) -- tambien aparece como rama `GASTO_PAGO_RECURRENTE` en `SP_PROYECTO_MOVIMIENTO_LISTAR` (solo instancias ya pagadas) y como barra en la seccion "Gastos" del detalle del proyecto.
  - **Parte de Cuentas por Pagar**: `SP_PAGO_RECURRENTE_INSTANCIA_LISTAR_PENDIENTES()` (cross-pago-recurrente, excluye pagadas/financiadas, solo pagos `ACTIVO`) es la sexta fuente de `/facturacion/cuentas-por-pagar`, mismo patron `FilaPendiente` que las otras cinco.

## Tipo de Cambio (Facturacion)

- **`/facturacion/tipo-cambio`** (app nueva `TIPO_CAMBIO`, area FACTURACION, pide `ADMIN` para fijar un TC nuevo -- afecta el costeo de cualquier proyecto que use esa categoria de ahi en adelante): resuelve de raiz el problema de mezclar monedas sin convertir (ver `031_tipo_cambio_proyecto.sql`/`033_ingreso_moneda.sql`) -- en vez de escribir el TC a mano cada vez en cada transaccion, cada campo "Tipo de cambio" del sistema ahora **se precarga automaticamente** con el TC vigente de su categoria, sin dejar de ser editable para corregirlo en esa misma transaccion (`defaultValue` en el input, no `readOnly`).
- **Cuatro categorias, fijadas automaticamente cada dia con el TC Venta de SUNAT** (`032_tipo_cambio_categorias.sql`, catalogo `MAESTRO_MAESTRO` `TIPO_MAESTRO='CATEGORIA_TIPO_CAMBIO'`): `LABORAL` (mano de obra manual de Proyectos), `PRESTAMO` (financiar con prestamo, las 4 pantallas de `FinanciarConPrestamoFila`), `COMPRA` (nueva compra) y `VENTA` (ingresos de Proyectos). Las 4 se fijan al mismo valor (el TC Venta oficial del dia -- criterio elegido por ser el que se usa tipicamente para convertir gastos en dolares a soles), pero siguen siendo corregibles por separado a mano en cualquier momento -- una correccion manual queda como la vigente de esa categoria hasta el proximo sync automatico o la siguiente correccion.
  - **"Vigente" = la fila mas reciente de un ledger, no una tabla de "valor actual"** (`TIPO_CAMBIO_HISTORICO`, mismo patron de solo-insertar que `RRHH_CONTRATO_HORAS`/`COMPRA_PAGO`): `SP_TIPO_CAMBIO_FIJAR` siempre agrega una fila nueva, nunca actualiza/borra una existente -- el historico completo queda solo, sin necesidad de una tabla aparte para current-value + otra para historial. `SP_TIPO_CAMBIO_LISTAR_CATEGORIAS` calcula el vigente de cada categoria con un subquery `ORDER BY FECHA_CREACION DESC LIMIT 1`. Las filas que pone el sync automatico quedan con `USUARIO_CREACION=NULL` (no se le atribuyen a quien haya cargado la pagina que disparo el sync) -- el historico en pantalla las muestra como "Automatico (SUNAT)".
  - **TC oficial SUNAT del dia, fetch + auto-fijado** (`TIPO_CAMBIO_SUNAT_DIA`, `src/lib/facturacion/tipo-cambio-sunat.ts` -> `asegurarTipoCambioDelDia()`, llamado desde `facturacion/layout.tsx`): sin cron real en esta app (Next.js + Server Actions, sin worker en segundo plano), "una vez al dia" se logra dejando que la primera visita del dia a **cualquier** pantalla de Facturacion (no solo `/facturacion/tipo-cambio`) dispare el fetch a `https://api.apis.net.pe/v1/tipo-cambio-sunat` (publica, sin API key) -- si ya existe una fila de `TIPO_CAMBIO_SUNAT_DIA` para hoy, no se vuelve a llamar (`FECHA` es la PK de la tabla, y el `INSERT` (`SP_TIPO_CAMBIO_SUNAT_GUARDAR_DIA`) ademas se guarda con `WHERE NOT EXISTS` por si dos requests casi simultaneos dispararan el fetch a la vez). Si la API falla (red, formato inesperado), no pasa nada -- las categorias se quedan con su ultimo valor vigente, corregible a mano igual.
  - **Boton "Actualizar TC ahora"** (`actualizarTipoCambioSunatAction`, pide `ADMIN`): vuelve a consultar la API aunque el sync automatico del dia ya haya corrido, y fija las 4 categorias de nuevo con el TC Venta obtenido -- para cuando SUNAT actualiza su tasa a media manana, o si el sync automatico fallo temprano y nadie mas visito Facturacion despues. A diferencia del sync automatico, esta version SI sobreescribe la fila de `TIPO_CAMBIO_SUNAT_DIA` de hoy (`SP_TIPO_CAMBIO_SUNAT_ACTUALIZAR_DIA`, `INSERT ... ON DUPLICATE KEY UPDATE`, a diferencia del `GUARDAR_DIA` no-op del sync automatico) y agrega una fila nueva al historico de cada categoria atribuida al usuario que lo presiono (no `NULL` como el sync automatico).
  - **Cada punto de captura del sistema que ya tenia un campo "Tipo de cambio" ahora lo precarga** con `obtenerTipoCambioVigente(codigo)` (repositorio nuevo, atajo sobre `SP_TIPO_CAMBIO_LISTAR_CATEGORIAS`): "Nueva compra" (`COMPRA`), "Mano de obra (asignacion manual)" e "Ingresos" en el detalle de un proyecto (`LABORAL`/`VENTA`), y las 4 instancias de `FinanciarConPrestamoFila` (`PRESTAMO`). Sigue siendo obligatorio solo cuando la moneda elegida difiere de la del proyecto (mismo guard no-op silencioso de antes) -- el precargado solo ahorra tener que escribirlo, no cambia cuando se exige.
  - **Ingresos de Proyecto ganan moneda propia** (`033_ingreso_moneda.sql`, cierra el hueco que quedo pendiente en el fix de monedas mezcladas anterior): `PROYECTO_INGRESO` ya no asume implicitamente la moneda del proyecto -- gana `ID_MONEDA`/`TIPO_CAMBIO` igual que `COMPRA`/`PROYECTO_COSTO_MANO_OBRA`/`PASIVO`, con backfill de la moneda del proyecto para las filas existentes. `SP_PROYECTO_INGRESO_AGREGAR` acepta `p_id_moneda` opcional (`NULL` = usa la moneda del proyecto, asi "Cobrar" un item del plan de facturacion -- que siempre cobra en la moneda del proyecto -- no tiene que resolverla por su cuenta). `INGRESO_REAL` y la fila `INGRESO` del ledger de Movimientos ya convierten con el mismo patron `CASE`/`TIPO_CAMBIO` que `COSTO_COMPRAS`/`COSTO_MANO_OBRA_MANUAL`.

## Contactos externos del Directorio

- **`DIRECTORIO_CONTACTO_EXTERNO`**: un solo modelo para las personas de contacto de un `CLIENTE`, de un `PROVEEDOR`, o de un **socio comercial**/otro (que no tiene tabla de entidad propia) — en vez de triplicar la misma tabla por cada tipo. `ID_TIPO_RELACION` (catalogo `TIPO_RELACION_CONTACTO`: `CLIENTE`/`PROVEEDOR`/`SOCIO_COMERCIAL`/`OTRO`) decide cual de `ID_CLIENTE`/`ID_PROVEEDOR`/`EMPRESA_EXTERNA` (texto libre) esta poblado — `SP_DIRECTORIO_CONTACTO_CREAR` fuerza a `NULL` los que no correspondan, y el tipo es inmutable una vez creado (mismo criterio que el tipo/banco/moneda de `CUENTA_EMPRESA`). Cada contacto lleva area/departamento, cargo, tema de interes y relacion con GT, todo texto libre (varia por empresa externa, no hay catalogo fijo razonable). Estas personas **nunca** pasan por `USUARIO` (no inician sesion) — el Directorio Corporativo de empleados (`RRHH_EMPLEADO`, atado 1:1 a `USUARIO`) no se toca en absoluto.
- **Se agregan desde la ficha de la empresa** — seccion "Contactos" en `/facturacion/proyectos/clientes/[id]` y en `/facturacion/compras/proveedores/[id]` — o desde `/rrhh/directorio/contactos/nuevo` (unico lugar para Socio comercial/Otro, con un selector de tipo que muestra condicionalmente el combo de Cliente, el de Proveedor, o un campo de texto "Empresa").
- **Visibles en `/rrhh/directorio`**, pestaña "Contactos externos" (antes "Contactos de clientes"), con chips de sub-filtro por tipo y un **avatar de color + etiqueta de texto por tipo** (nunca solo color) para diferenciarlos de un vistazo del personal de GT: azul = Personal GT, esmeralda = Cliente, ambar = Proveedor, morado = Socio comercial, gris = Otro (`src/lib/directorio/tipo-contacto.ts`). Detalle en `/rrhh/directorio/contactos/[idContacto]`, con link de vuelta a la empresa cuando aplica (Cliente/Proveedor).
- **Permiso segun el tipo, no una app nueva** (`src/lib/actions/directorio-contacto.ts`): un contacto de `CLIENTE` se administra bajo `PROYECTOS_EMPRESA`, uno de `PROVEEDOR` bajo `COMPRAS_EMPRESA`, y uno de `SOCIO_COMERCIAL`/`OTRO` (sin modulo dueño) bajo `RRHH_DIRECTORIO` — las tres acciones compartidas (`crear`/`actualizar`/`cambiarEstado`) resuelven el permiso a exigir leyendo el `tipoRelacionCodigo` que llega en el formulario, en vez de tener nueve acciones casi identicas repetidas por modulo.

## Refrescar la pantalla despues de una mutacion

- Esta version de Next.js (16) separa dos cosas que en versiones anteriores se confundian: `revalidatePath()`/`revalidateTag()` (de `next/cache`) invalidan el cache de datos para **futuras** visitas a esa ruta, pero no garantizan que la pantalla en la que el usuario ya esta forzosamente se vuelva a pintar con datos frescos. Para eso existe `refresh()` (tambien de `next/cache`, solo se puede llamar dentro de una Server Action): "refresca el router del cliente" para que la pantalla actual muestre el resultado de la mutacion sin que el usuario tenga que salir y volver a entrar.
- **Toda Server Action que muta datos y no hace `redirect()` despues llama `refresh()` justo despues de sus `revalidatePath(...)`** (ver cualquier archivo en `src/lib/actions/`). Las que si hacen `redirect()` (crear proyecto, crear compra, crear contrato, etc.) no necesitan `refresh()` — navegar a una URL nueva ya trae datos frescos por si solo.
- Si agregas una Server Action nueva que mute datos y quede en la misma pantalla (no redirige), agregale `refresh()` al final — si se te olvida, la tabla/seccion afectada solo se va a actualizar cuando el usuario navegue fuera de la pantalla y vuelva a entrar.

## Combos con busqueda

- Todo `<select>` que lista filas de la BD (maestros, clientes, proveedores, cuentas, usuarios, roles, contratos, proyectos, etc.) usa `ComboBusqueda` (`src/components/ui/ComboBusqueda.tsx`) en vez de un `<select>` nativo — es un input de texto que filtra la lista mientras se escribe y manda el valor elegido en un `<input type="hidden">` con el mismo `name`, asi que funciona dentro de cualquier `<form action={serverAction}>` sin cambios en la action. Selects controlados que antes usaban `onChange` (para mostrar/ocultar campos segun lo elegido, ej. tipo de cuenta, tipo de contrato) pasan su `onSeleccionar` en vez de `onChange`.
- Quedan como `<select>` nativo solo los catalogos muy chicos (2-5 opciones fijas) donde escribir para filtrar no aporta nada, por ejemplo el nivel de permiso por fila en `/administracion/permisos` — ademas ese select vive dentro de una tabla con `overflow-x-auto`, donde la lista flotante de `ComboBusqueda` se recortaria visualmente.
- `ComboBusqueda` no reproduce la validacion nativa `required` del navegador (el value real viaja en un input oculto, que el navegador no valida) — no es un problema porque todas las server actions ya validan los campos obligatorios a mano y no hacen nada si falta alguno (mismo criterio de "no-op silencioso" que el resto del sistema).

## Manejo de errores

- **`error.tsx` por segmento, no un crash entero**: `src/app/(intranet)/error.tsx` (cubre RRHH/Facturación/Administración) y `src/app/contratos/error.tsx` (cubre el flujo publico de firma, sin login) son limites de error de Next — si una Server Action o un Server Component lanzan un `Error` no controlado, en vez de que la pantalla se caiga entera se ve una tarjeta con el mensaje y un boton "Reintentar", dentro del mismo layout (sidebar/topbar en el caso de intranet). **Ojo con el nombre del prop**: esta version de Next (16.2+) cambio `reset` por `unstable_retry` en `error.tsx` — no es lo que dice el training data, revisa `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md` si hace falta agregar otro.
- **Cuando una Server Action debe lanzar `Error`**: cuando una SP hace no-op silencioso sobre una condicion que la app ya debería haber evitado (ver convencion "no-op silencioso" mas abajo), la capa de repositorio (`src/lib/db/repositories/*.ts`) revisa el `OUT` param y lanza `throw new Error("mensaje legible")` si quedo `NULL` (ver `crearPasivo`, `crearContrato`, `agregarProyectoContrato`) — el `error.tsx` del segmento lo atrapa y lo muestra. Para condiciones que la propia app puede detectar **antes** de llamar al procedimiento (ej. un valor fuera del rango de una columna `DECIMAL`, que si no se valida termina en un `ER_WARN_DATA_OUT_OF_RANGE` crudo de MySQL), valida en la Server Action y lanza el `Error` ahi mismo con un mensaje de negocio en vez de dejar que el error del driver llegue tal cual (ver el guard de `porcentaje` en `agregarHitoProyectoAction`, `src/lib/actions/proyectos.ts`).
- **No es el patron recomendado por Next para validacion** (`useActionState` + retorno de estado, ver `node_modules/next/dist/docs/01-app/02-guides/forms.md`) — se eligio `throw` porque ya es el patron establecido en todo el codebase (formularios simples con `<form action={serverAction}>`, no client components con estado) y migrar todo a `useActionState` es un cambio mucho mas grande. El `error.tsx` por segmento es la red de seguridad minima para que ese patron no termine en una pantalla rota.
- **Los mensajes de error pueden resumirse en produccion**: la documentacion de Next confirma que los errores que llegan al cliente desde un Server Component compilado en produccion se redactan a un mensaje generico + `error.digest` (identificador para cruzar con los logs del servidor) — en desarrollo se ve el `message` completo. No esta confirmado en la documentacion de esta version si una Server Action invocada por un `<form action={...}>` sigue exactamente la misma regla, asi que verificalo en un build de produccion real antes de asumir que un mensaje pensado para el usuario (ej. "El porcentaje debe ser mayor a 0...") se ve completo ahi tambien.
